# 大改修: 5インフラ制約起点の再設計 — 調査と方針（idea）

作成: 2026-08-02。状態: idea（owner 判断待ち）。
調査は working tree（5基盤実測完了・実験管理/パイプライン EL4 検証済み時点）に対して実施。
主張はすべて file:line と `docs/comparison/` の実測を出典とし、推測で書いていない。

## 0. 依頼と前提

> MLコードは5つのインフラすべてで共通に使う。だからこそ、MLコードを起点に設計してはならない。
> 依存先である5つのインフラの制約から出発し、「共通MLコードはどうあるべきか」を逆算して定義する。
> 設計は、各インフラの特徴と2系統（Tier A: Vertex/SageMaker/AzureML 系、Tier B: Databricks/Snowflake 系）の
> 差異を「どの層で・どう吸収するか」を決めるところから始める。

この導出順序自体は既に正本化されている（[02_architecture.md「設計の導出順序」](../../02_architecture.md)、
[decision-log 2026-08-02「設計の向きを反転する」](../../decisions/decision-log.md)）。
したがって本調査の問いは「原則を作るか」ではなく:

1. **現構造のどこが、この導出順序にまだ従っていないか**（歴史的に Phase 0 = ローカルMLコードが
   最初に書かれ、制約の実測は後から来た。逆向きに作られた層が残っていて当然）
2. **なぜ新機能のたびに inside-out 設計が再発するのか**（2026-08-02 だけで実験管理・パイプライン・
   記録スパインの3件が「実装 → owner 指摘 → 再設計」を繰り返した）

## 1. 調査の結論（TL;DR）

**`core/ml`（約620行）自体は、既に逆算の帰結どおりの形に収まっている。壊れているのはその周りの
吸収層の「配置」と「単一正本性」である。** 大改修の対象は共通MLコードの書き直しではなく、
層の再配置・実行境界の統合・正本の一本化の3点。

| # | 発見 | 深刻度 | 種別 |
|---|---|---|---|
| 1 | 計測スパイン（`core/telemetry`）が5基盤の分類軸・Neon 到達経路をハードコードしたまま **core を名乗っている** | 高 | 誤配置 |
| 2 | 学習実行の入口が **3系統に分裂**し、`MlRun` 構築が3実装。うち Snowflake は**ジョブ内失敗を記録できない**（一次データの欠落 = 実害） | 高 | 分裂 |

## 2. 手順1: 5インフラの制約（実測で確定済みの入力）

詳細は `docs/comparison/01〜05` が一次記録。再設計の入力として効く制約だけ再掲する。

| 基盤 | 持ち込み単位 | 起動契約 | 依存の自由度 | egress / Neon | 登録の契約 |
|---|---|---|---|---|---|
| Vertex | BYOC イメージ | env（`AIP_MODEL_DIR`、gs://→/gcs 変換要） | 完全 | direct | URI を渡すだけ |
| SageMaker | BYOC イメージ（**schema2 のみ・非 root 不可**） | 固定パス `/opt/ml/*`・**引数不可**（文字列 hyperparameters） | 完全 | direct | URI・0.78s |
| Azure ML | BYOC イメージ | マウント宣言→置換引数（**モデルが1段深く残る**） | 完全 | direct | URI |
| Databricks | wheel（UC Volume。**FUSE seek 不可**） | entry point 関数呼び出し（**SystemExit 必須・SystemExit(0) は失敗**） | Runtime + Python 本体版に従属 | collected（psycopg 不在 + trusted domains） | MLflow client のみ・signature 必須・**登録にジョブがもう1本要る** |
| Snowflake | zip → stage（auto_compress=False） | SQL DDL + `main(session, params)` | **最弱**（Anaconda channel 在庫 × SDK 要求。sklearn の版は5基盤ここが決めた） | collected（EAI がトライアル不可 = **契約の壁**） | 復元済みモデル + sample + conda 依存（最重） |

共通コードに効く制約トップ10 は既に 02_architecture 手順4と `ports.py` / 番人テストに落ちており、
**手順4の「逆算された要求」への違反は `core/ml` には見つからなかった**。
（依存 allowlist・URI 非知・記録分離・CLI 契約・基盤名分岐なし — すべて番人テストが実在し緑。）

## 3. 手順2: 2系統の差の本質と、構造への反映方針

実測が示した Tier 分けの本質は、配布形式（コンテナ vs wheel/zip）ではなく
**実行環境の所有権が誰にあるか**。そこから3つの一次差が従う:

1. **依存解決の時点**: A = ビルド時に確定（失敗はイメージ受理の契約に出る）。
   B = **サーバ側で後段解決**（クライアント成功→登録/serving で落ちる。Snowflake の PyPI 経路・
   Databricks の CondaEnvException が同型）
2. **登録の情報量**: A = URI を渡すだけ。B = モデルを**理解させる**（signature・依存宣言）
3. **egress**: A = 開、B = 宣言的オブジェクト経由か閉（→ write_path 系統差）

**判断: Tier をパッケージ構造（`platforms/tier_a/` のような層）には昇格させない。**

- Tier 内差が Tier 間差より大きい軸が実在する（Databricks は PyPI 可・Snowflake は不可 /
  ジョブ資源の有無 / destroy の壊れ方）
- 「できない」の正体が契約プランである壁は Tier をまたいで3基盤で起きた
- 差そのものが成果物であり、Tier 抽象の下に隠すと比較軸が消える（`ports.py` の port 基準と同じ理屈）

Tier は**データ（分類ラベル）と、差ごとの吸収メカニズムの選択**に留める。吸収は「Tier 単位」でなく
「差分単位」で決める — これは 02_architecture 手順3の現行方針の追認であり、変更しない。

## 5. 大改修の方針（優先順・依存関係つき）

方針の背骨: **「共通MLコード」の定義を『5ランタイム全部で import できる stdlib/最小依存のコード』
（依存都合）から『5インフラの制約の交差点だけを含むコード』（責務）へ引き直す。**
その結果として層は4つになる:

```text
core/           交差点のみ（ml + app）。基盤を知らない。依存は実測の積集合
telemetry/      計測スパイン（本ラボの計測装置の正本。5基盤を知る。stdlib のみは維持）
platforms/      基盤ごとの差（adapter・runtime 入口・neon・shared契約）
配布層           image / wheel / zip / Makefile — すべて pyproject と packaging_names から導出
```

### P0. 即修理（大改修と独立。先に単体で直す）

- `Makefile:154` `from platforms.config import ...` → `platforms.shared.config`（`make dbx-upload` が現に ImportError）
- `Makefile:157` の wheel ファイル名直書き → `packaging_names.wheel_filename()` 経由
- `env/config.yaml:63` `azureml.experiment_name` → `experiment`（無言 drop の実害）
- docstring drift 4件（`vertex/adapter.py:330` の Stage.TEARDOWN 矛盾、`training/Dockerfile:39` の「未配線」、`resume.py:22` の消滅関数参照 ほか）

### P1. 実行境界の統合 — ジョブ側入口を1つの Python 境界へ（最重要・正しさの改修）

**何を**: `platforms/runtime/`（仮名）を新設し、「引数/JSON/VARIANT を受ける → `core.ml` を呼ぶ →
成功・失敗を問わず `MlRun` を1実装で組む → sink（Neon direct / JSONL collected）へ流す →
基盤の期待する形で終了を返す」を一本化する。5基盤の入口は薄い翻訳だけになる:

| 基盤 | 入口に残るもの（基盤固有の翻訳のみ） |
|---|---|
| Vertex シム | `AIP_MODEL_DIR` gs://→/gcs 変換 |
| SageMaker シム | `/opt/ml/*` 固定パス・hyperparameters.json の読み・`/opt/ml/output/failure` 書き |
| Azure シム | 置換済み引数の横流し（ほぼ消滅） |
| Databricks `job_main` | SystemExit 翻訳（成功時は送出しない・失敗時のみ SystemExit） |
| Snowflake `sproc_handler` | Session 注入からの DataFrame 取得・stage への PUT |

**なぜ**(逆算): 起動契約の差は手順3で「シム層で吸収」と決めた差である。現状はその吸収層自体が
4重実装で、吸収ロジック（引数契約・MlRun 構築・exit code 翻訳）が翻訳（基盤固有部分）と
混ざっている。差でない部分が複製されているのは吸収の失敗。

**これで直る実害**: Snowflake の失敗未記録（統一入口が try/except で包み、失敗時も JSONL を
stage へ PUT してから基盤の失敗形式で返す）。`--attempt` の3重横流しも消える。

**番人**: 「5入口すべてが同一の runtime 関数を呼ぶ」「MlRun 構築関数は repo に1つ」を AST 検査。
既存の `test_code_revision_parity`（tree hash）は `src/core/ml` 対象なので**この改修では動かない**。

**制約**: runtime は Snowflake warehouse でも動く必要がある → stdlib + （Neon direct 時のみ遅延
import の psycopg）。これは既存 `job_record.py` と同じ制約で、実装の大半は job_record の昇格。

### P2. 計測スパインの再配置 — core を「交差点のみ」に縮める

**何を**: `core/telemetry` → トップレベル `src/telemetry/`（または `platforms/measure/`）へ移設。
Platform/Tier/WritePath/PLATFORM_TIER は計測スパインの正本としてそこに置く。
`core/` は `ml` + `app` だけになり、「core は基盤を知らない」が enum レベルでも真になる。

- `core/app` の残る漏れ2点も同時に処置:
  - `predictor.resolve_model_dir()` の3 env 名 → serving 起動シム（`docker/serving/entrypoint.sh`）が
    env を正規化して `MODEL_DIR` 一本にし、core は `MODEL_DIR` しか読まない
    （gs:// 取得を既にシムでやっている構造の延長。`locate_model_file` の1段探索は
    「レイアウトの和集合を受ける」交差点として残す — Azure の1段深さは実クラウドでしか
    出なかった実測であり、テスト `test_predictor.py` の LAYOUTS parametrize を正本のまま維持）
  - `observability/logging_setup.py` の GCP trace 固有部 → 全基盤で無害な構造化ログ +
    GCP 拡張はシム側 env で有効化
- `core/ml/config/constants.py:10` の `DATASET_NAME = "neon.mlcompare..."` → 供給側（distribute /
  adapter）へ移す

**影響の明示**: `src/core/ml` 配下を1文字でも動かすと tree hash が変わり、旧 run との resume 互換は
切れる（記録済み実測値は不変・parity テストはスナップショット対象なので壊れない）。
constants.py の変更がここに該当。**移設後の新 hash で以後の run が揃えば比較は成立**（担保単位は
「同一 SHA」であって「特定の SHA」ではない）。

**番人**: `test_core_boundaries` の対象を core 全体へ拡大（telemetry 除外だった platform 名検査を
不要にする）。「core 配下に Platform enum・基盤 env 名が存在しない」を追加。

### P3. 単一正本化 — 依存 pin と serving 契約

**何を**:
1. 依存6箇所を pyproject 起点の導出 or 契約テストで束ねる。生成（テンプレート化）までやるかは
   費用対効果で判断だが、最低限 `test_packaging_contract` を `SPROC_PACKAGES` /
   `MODEL_CONDA_DEPENDENCIES` / `SERVING_PIP_REQUIREMENTS` / orchestrator Dockerfile まで拡張し、
   「lightgbm を上げるとき6箇所のどれかを忘れると赤」にする。
   形式差（channel 名・`==` pin）は変換表を正本化して吸収する
2. serving のルート/ポートを `core/app` の公開定数にし、`VertexConfig` / azureml 定数は
   それを import（platforms→core は合法方向）。Dockerfile の 8080 は契約テストで突き合わせ
3. Neon env 名 3定義 → 1定数（psycopg 非依存の場所 = P2 の telemetry へ）+ 一致テスト

**なぜ**(逆算): 「同一SHA・同一依存で5基盤の RMSE が一致する」が比較成立の担保
（01_requirements 破綻条件）なのに、その前提の担保が grep と人力になっている。

### P4. 契約外経路と非対称の解消

1. **パイプライン経路**: `run_pipeline.py` が Protocol 越しでなく**具象 adapter 型**を明示的に
   受け取る形へ（パイプラインは3基盤で形が違う=非対称が正、と既に決めた領域。無理に
   `PlatformAdapter` を太らせるのは all-or-none 規則違反になる）。`_config` 直叩きは
   adapter に公開プロパティ（`service_account` 等、パイプライン組成に要る値）を**基盤別に**生やして解消
2. **config.yaml platform 節の無言 drop 廃止**: common 節と同じ「未知キーは ConfigError」へ。
   `test_platforms_config` に config.yaml 側の検査を追加
3. **handoff キーの一本化**: `deploy_reference` と `MODEL_REFERENCE_KEYS` を factory の単一
   対応表に統合し、SageMaker の「書くもの≠deploy が使うもの」非対称を1箇所で明示

### P5. adapter 重複の刈り込み（最後・慎重に）

逐語一致の7パターン（`model_artifact_uri` ラッパ・`_endpoint_exists`・空 predictions ガード・
`_Entities` 遅延 import 窓口 等）のうち、**「5基盤で意味まで同一」なものだけ** `TrackedOperations` /
shared ヘルパへ。`ports.py` の基準（差を隠さない）に照らし、1つでも意味が違うものは残す。
早すぎる共通化はこの repo で繰り返し戒めてきた失敗形なので、P1〜P4 の後に、
`plan-refactor` スキルの手順で個別判定する。

### 実施順序と規模感

```text
P0（即・1セッション以内）→ P1（Heavy・実行境界）→ P2（Heavy・core 縮小）→ P3 → P4 → P5
                                └ P1 と P2 は独立に見えるが、runtime が telemetry を import する
                                  ため P2 の置き場を先に決めてから P1 を実装するのが手戻りゼロ
```

- P1・P2 は Weight Class Heavy。SPEC.md → skeleton → TDD contract の正規手順で、各1本の task として実施
- **全フェーズ共通の不変条件**: ① 記録済み実測値・`docs/comparison/` は書き換えない
  ② `make test` の parity / boundary / asymmetry 系は常時緑 ③ 挙動変更を伴うのは
  Snowflake 失敗記録（P1・意図した仕様修正）のみで、他はすべて等価変形
  ④ 実クラウド検証（EL4）は P1 完了後に1回、5基盤 run の再実行とまとめて実施
  （静的検証で閉じない主張を作らない — 修正11 の教訓）

## 6. 再発防止（プロセス側の根本対策)

2026-08-02 の3連続の inside-out は、能力の問題ではなく**入口の問題**。導出順序は文書として
存在するが、新機能の作業手順に組み込まれていない。対策:

1. **SPEC.md テンプレートに「制約表」節を必須化**: 実装対象の機能について、5基盤それぞれの
   制約（SDK の形・持ち込み単位・egress・契約プラン）を**先に**埋める。埋まらない行は
   「実測が要る」と書く。共通層に触る設計は、この表で「5基盤に同型の実装が並ぶ」ことを
   示せた場合のみ許す（`ports.py` の port 基準の作業手順化）

   P1〜P4 の各改修で必ず対応する番人を1本以上足す（上記各節に記載）
3. **distilled-memory への蒸留**: decision-log に成熟した原則が3つ溜まっている
   （交差点原則・片実装を契約で均さない・1基盤の結論を転移しない）。`distill-memory` で
   `docs/memory/distilled-memory.md` へ昇格する（現状0件）
