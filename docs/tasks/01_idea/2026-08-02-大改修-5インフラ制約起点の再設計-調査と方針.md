作成: 2026-08-02（第1回）→ 同日 第2回調査で全面改訂。状態: idea（owner 判断待ち）。

**第2版の位置付け**: 第1回の調査・方針に対し、(a) 方針 P1〜P3 の**敵対的な反証検証**（配布物の実物・import グラフ・実 zip の中身）、(b) 第1回で手薄だった **infra / scripts / sql / 配布層**の調査、(c) **番人テストと設計規則の突き合わせ監査**（`make test` / `make lint` 実行込み）の3本を実施して書き直したもの。**第1回の主張のうち3件が反証され、事実誤りを複数訂正した**（§2）。外れた予想も残す文化に従い、訂正は消さず明記する。

## 0. 依頼と前提

> MLコードは5つのインフラすべてで共通に使う。だからこそ、MLコードを起点に設計してはならない。
> 依存先である5つのインフラの制約から出発し、「共通MLコードはどうあるべきか」を逆算して定義する。
> 設計は、各インフラの特徴と2系統（Tier A: Vertex/SageMaker/AzureML 系、Tier B: Databricks/Snowflake 系）の
> 差異を「どの層で・どう吸収するか」を決めるところから始める。

導出順序自体は正本化済み（[02_architecture.md「設計の導出順序」](../../02_architecture.md) /
[decision-log 2026-08-02「設計の向きを反転する」](../../decisions/decision-log.md)）。よって本調査の問いは:

1. 現構造のどこが、この導出順序にまだ従っていないか
2. なぜ新機能のたびに inside-out 設計が再発するのか（8/2 だけで3回反復）
3. **（第2回で追加）その導出順序を書いた正本と番人テスト自体は信頼できるか**

## 1. 結論（TL;DR・第2版）

**`core/ml`（約620行）は逆算の帰結どおりで、書き直す理由がない。** 大改修の対象は共通MLコードではなく、その周りの (a) 吸収層の配置と分裂、(b) 単一正本性、(c) **正本ドキュメントと番人テスト自体の劣化**、(d) **計測経路の完全性**（第2回で発見）の4点。

第2回で構図が変わった点:

- **正本が古い**: 02_architecture 手順3表の Vertex パイプライン行は「見送り（P3）」のままだが、実装は owner 指示で撤回済み（orchestrator 実在・番人も「器を使うこと」を pin）。**大改修の土台となる表が実装と矛盾している**。「5基盤レイアウト parametrize」の記述も実物は3基盤。
- **番人の一部は空振り**: `make test` は 647 全緑・33s だが、①同一SHA担保の中核 assert（`test_code_revision_parity` の tree 一致）は履歴リセットの帰結で**一度も実行されない**（早期 return）、②基盤名分岐の AST 検査は**語彙から `databricks` が欠落**し `ast.If` のみ・`core/ml` のみ、③実験追跡の番人は緑のまま config.yaml の死にキーを見逃している。**「647 緑」は「規則が守られている」を意味しない**（evidence-policy の「緑のワークフローは最大 Level 1」がそのまま当てはまる）。
- **計測の標準経路に穴**: `make tf-destroy` が `check-residual --record` を呼ばず、**残留の一次データが標準経路では infra_events に書かれない**（runbook の手打ちだけが記録している）。`collect_costs` の Vertex/Azure は構造的に到達不能、Snowflake は別スクリプトが実測で禁じた `getOrCreate()` を使用。
- **死んだ実行経路が5つ**: `make dbx-upload`（ImportError で必ず失敗）/ `make tf-init`（全5環境で失敗）/ `make distribute` の `--all`（到達不能）/ `collect_jsonl --platform`（実装なし exit 2）/ `collect_costs` の Vertex・Azure。
- **第1回方針への反証3件**（§2）により、旧 P1 の主目的（Snowflake 失敗記録）は行所有規約の改訂なしには達成されず、改修パッケージの優先順位を再構成した（§6）。

## 3. 手順1・手順2: 制約と系統差（第1版から維持・要点のみ)

5基盤の制約実測の要約と「共通コードに効く制約トップ10」は第1版どおり（出典: `docs/comparison/01〜05` / 02_architecture 手順1〜4）。要点:

- Tier 分けの本質は配布形式ではなく**実行環境の所有権**。そこから (1) 依存解決の時点（A=ビルド時 / B=**サーバ側で後段解決** — クライアント成功→後段で落ちる同型が2基盤で実測）、(2) 登録の情報量（A=URI / B=モデルを理解させる）、(3) egress（A=開 / B=宣言的 or 閉）が従う。
- **判断（維持）: Tier をパッケージ構造に昇格させない。** Tier 内差（PyPI 可否・ジョブ資源の有無・destroy の壊れ方）が Tier 間差より大きい軸が実在し、契約プランの壁は Tier をまたぐ。差そのものが成果物である以上、系統は抽象でなく**データと差分単位の吸収**に留める。
- `core/ml` 内の基盤都合の吸収3点（ディレクトリ受け・小文字化・型復元）は**交差点として正当**（基盤名を持たない和集合受け）。維持。

## 5. 大改修の方針（第2版・優先順）

#### D1. owner 判断: Snowflake のジョブ内失敗一次データ

| 選択肢 | 内容 | 帰結 |
