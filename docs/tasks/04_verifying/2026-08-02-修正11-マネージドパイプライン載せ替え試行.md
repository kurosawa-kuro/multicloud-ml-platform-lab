### なぜ Core 変更ゼロで載るか

1. **オーケストレータは既に Core の外。** `PlatformAdapter`（`ports.py`）は5操作の形だけを
   規定し、呼び出し元を規定しない
2. **全 stage が別プロセスで独立実行できる**（修正07 の成果）。register は `artifact_uri` を
   Neon から resume するので、**ステップ間で KFP の artifact を配線する必要がない**
3. **Tier B は additive change の外側。** Databricks / Snowflake は誰が Vertex を
   回しているかを知らない

### env-conf での制御は要らない（owner の問いへの答え）

「パイプライン的にふるまうか否か」は adapter の性質ではなく**起動時にどのドライバを
呼ぶかの選択**（`make phase-train` ↔ `make pipeline-compile` → 投入）。
adapter は同じコードが動くので実行時フラグで分岐させるものが無く、実装でもそうなった。
config 分岐で adapter に `if` を増やす方が「1操作 = 1行」の意味論を濁らせる。

## 実装（2026-08-02・main 直コミット）

| ファイル | 役割 |
|---|---|
| `src/platforms/vertex/pipeline.py` | パイプライン定義。ステップ = 既存イメージ + `run_phase.py vertex <stage>` |
| `scripts/compile_pipeline.py` | compile の入口。ローカルで解決した Vertex 設定を `MCML_VERTEX_*` へ載せ替える |
| `Makefile` | `make pipeline-compile`（**投入はしない**・課金ゼロ） |
| `pyproject.toml` | `pipelines = ["kfp>=2.14,<2.15"]`。**`gcp` extra には入れない**（既定の実行経路は kfp を import しない） |
| `tests/platforms/test_vertex_pipeline.py` | 10 件 |

### 設計上の要点

- **ステップ間で KFP の artifact を渡さない。** 受け渡しの正本を Neon に一本化しておくと
  CLI 実行とパイプライン実行で経路が変わらない（＝ KFP 固有の配線を作らない）
- **キャッシュは既定で無効。** 命中すると「実行していない成功」が生まれ、`ml_runs` に
  行が無いまま次へ進む。attempt の連番と実行実態がずれ、permission friction が濁る
- **env は設定と秘密だけを通す。** ジョブ定義はコンソールから読めるので手元の環境を
  丸ごと載せない。`CODE_REVISION` も渡さない（コンテナに焼いた値を上書きすると
  「実際に動いたコード」と記録がずれる。`telemetry_env` と同じ判断）
- 設定はコンテナ内に terraform outputs が無いため `MCML_VERTEX_<FIELD>` で渡す。
  これは `config.py` の解決順の第1候補で、**規約を曲げていない**

### 実装中に踏んだ落とし穴（記録）

1. `dsl.container_component` は **戻り値注釈 `-> dsl.ContainerSpec` が必須**。無いと
   `Artifacts must have both a schema_title and a schema_version. Got: str` で落ちる
2. **`from __future__ import annotations` があると同じエラー**になる。PEP 563 で注釈が
   文字列化され kfp が解決できないため、`pipeline.py` だけこの import を入れていない
3. kfp 2.14 は **JSON 出力が deprecated**。`.yaml` で出す
