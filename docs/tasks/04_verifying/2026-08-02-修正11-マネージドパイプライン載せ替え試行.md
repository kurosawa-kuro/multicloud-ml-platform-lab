## 結論（2026-08-02 実クラウドで反証）: **「既存イメージで載る」は誤りだった**

compile は通ったが、**投入すると `run-stage` が exit status 2 で即失敗**した
（PipelineJob `mcml-vertex-train-register-20260802022521` / state=FAILED）。

原因はイメージの中身。学習イメージには **`scripts/` も vertex adapter も
`google-cloud-aiplatform` も入っていない**（実測）:

```
$ docker run --rm --entrypoint sh mcml-training:latest -c 'ls /app; ls /app/src/platforms'
/app       … README.md entrypoint_*.sh pyproject.toml src   ← scripts/ が無い
platforms  … __init__.py neon                                ← vertex adapter が無い
$ python -c "import google.cloud.aiplatform"  → ModuleNotFoundError
```

これは事故ではなく **設計どおり**。`docker/training/Dockerfile` は `src/core` と
`src/platforms/neon` だけを入れる。`pyproject.toml` の `gcp` extra にも
「**学習コンテナには入れない**（core/ml の依存最小制約）。adapter はジョブを投げる側＝
ローカル/オーケストレータでのみ import される」と明記されている。

### 何を読み違えたか

再調査で「オーケストレータは Core の外」「stage は別プロセスで独立実行できる」までは
正しかった。**しかし「別プロセスで動く」と「学習イメージの中で動く」は別**である。
`run_phase.py` はオーケストレータ側のコードで、学習コンテナは**オーケストレータに
なれるように作られていない**。compile が通ったのは、KFP が image と command の
文字列を検証しないから —— **静的検証の射程外だった**。

「ブランチを切らなくても調査で分かる」は修正10 では正しかったが、
本タスクでは **compile 成功を「組めた」と読んだのが早計**だった。実投入が反証した。

## 正しい形（未実装・次の判断材料）

パイプラインのステップには **オーケストレータイメージ**が要る。要件:

- `scripts/run_phase.py` と `src/platforms/{shared,vertex}`
- `gcp` extra（`google-cloud-aiplatform`）と `neon` extra（`psycopg`）
- 学習イメージとは**別物**（依存最小の制約を壊さないため統合しない）

これは「新しいイメージを1つ増やす」話であって Core の変更ではない。
ただし **`docs/comparison` の「統一単位 = コンテナ」の意味が1つ増える**ので、
比較の記述に影響する。owner 判断が要る。

### 選択肢

- **P1. オーケストレータイメージを足す**: Dockerfile 1枚 + push 経路。
  パイプライン化の本来の姿だが、ビルド対象が3つ（training / serving / orchestrator）に増える
- **P2. ステップを「学習イメージが直接できること」に寄せる**: ステップ = 学習 CLI そのもの
  （`python -m core.ml.cli` + `job_record`）にし、register 以降はパイプライン外。
  DAG の価値がほぼ無くなる
- **P3. パイプライン化を見送る**: 実測で「載せるには器を1つ増やす必要がある」と分かった。
  得られる DAG 管理の価値と釣り合うかは owner 判断
