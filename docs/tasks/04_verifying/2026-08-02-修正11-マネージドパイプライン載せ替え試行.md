### 実装の要点

- ステップに載せるのは `SageMakerAdapter.training_request()` /
  `AzureMLAdapter.training_job()` の戻り値 —— **CLI 投入とまったく同じ関数**。
  別々に組むと「CLI では通るがパイプラインでは落ちる」差が生まれ、比較が濁る
- 学習イメージは不変なので entrypoint シムと `job_record` はそのまま動く

- `TrainingJobName` は定義から外す（Pipelines が実行ごとに採番。固定名だと2回目が衝突）
- register / deploy は入れない（**常時課金**。見たいのは「学習が同じ意味論のまま
  パイプラインから起こせるか」だけ）

## 結論（2026-08-02 実クラウドで反証）: **「既存イメージで載る」は誤りだった**

compile は通ったが、**投入すると `run-stage` が exit status 2 で即失敗**した
（PipelineJob `mcml-vertex-train-register-20260802022521` / state=FAILED）。

原因はイメージの中身。学習イメージには **`scripts/` も vertex adapter も
`google-cloud-aiplatform` も入っていない**（実測）:

```
$ docker run --rm --entrypoint sh mcml-training:latest -c 'ls /app; ls /app/src/platforms'
/app       … README.md entrypoint_*.sh pyproject.toml src   ← scripts/ が無い
platforms  … __init__.py neon                                ← vertex adapter が無い
$ python -c "import google.cloud.aiplatform"  → ModuleNotFoundError
```

これは事故ではなく **設計どおり**。`docker/training/Dockerfile` は `src/core` と
`src/platforms/neon` だけを入れる。`pyproject.toml` の `gcp` extra にも
「**学習コンテナには入れない**（core/ml の依存最小制約）。adapter はジョブを投げる側＝
ローカル/オーケストレータでのみ import される」と明記されている。

### 何を読み違えたか

再調査で「オーケストレータは Core の外」「stage は別プロセスで独立実行できる」までは
正しかった。**しかし「別プロセスで動く」と「学習イメージの中で動く」は別**である。
`run_phase.py` はオーケストレータ側のコードで、学習コンテナは**オーケストレータに
なれるように作られていない**。compile が通ったのは、KFP が image と command の
文字列を検証しないから —— **静的検証の射程外だった**。

「ブランチを切らなくても調査で分かる」は修正10 では正しかったが、
本タスクでは **compile 成功を「組めた」と読んだのが早計**だった。実投入が反証した。

## 判定: **P3 見送り**（owner 承認 2026-08-02）— 実装は撤去した

パイプラインのステップには **オーケストレータイメージ**（`scripts/run_phase.py` +
`src/platforms/{shared,vertex}` + `gcp`/`neon` extra）が要る。学習イメージとは別物で、
依存最小の制約を壊さないため統合もできない。

### なぜ P1（イメージを足す）を選ばなかったか

- 本ラボは**5基盤の比較レポートが成果物**で、比較はすでに完了している。
  パイプライン化で得られる DAG 管理・スケジュールは、2 stage の流れに対して
  `run_phase.py all` が既に果たしている
- ビルド対象が training / serving / **orchestrator** の3つに増え、
  `docs/comparison` の「統一単位 = コンテナ」の意味も1つ増える。
  **比較の記述を濁す代償**が、得られる価値に見合わない
- P2（ステップを学習 CLI そのものに寄せる）は DAG の価値がほぼ消えるので論外

**得られた成果は「載せるには器を1つ増やす必要がある」という実測**であり、
それは記録として残る。コードを残す必要は無い。

### 実装を撤去した理由

このリポは §2.3 で「`ArtifactStore` を実装したのに実行経路から呼ばれていない」ことを
**port を切ったのに配線しなかった**欠陥として自己批判している。**動かないと実測で
分かったパイプライン定義を残すのは、その死蔵そのもの。** 撤去した:

- `src/platforms/vertex/pipeline.py` / `scripts/compile_pipeline.py`
- `tests/platforms/test_vertex_pipeline.py`（10 件）
- `Makefile` の `pipeline-compile` / `pyproject.toml` の `pipelines` extra

再挑戦するときは本ノートの §実測ログ から始められる（器の要件は上に書いてある）。
