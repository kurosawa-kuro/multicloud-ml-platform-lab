## 判定根拠

### なぜ実験（PoC ブランチ）が要らなかったか

記録先は `RunSink` **Protocol**（`core/telemetry/tracking.py:85`）で既に抽象化されており、
`NeonRunSink` / `JsonlRunSink` がこの契約の下で差し替わっている（`write_path` の
direct / collected はこの差し替えそのもの）。**Experiments を「もう1つの記録先」として
足せるかは、契約を読めば確定する**。実際、実装は decorator 1枚で済み、
`PlatformAdapter` / `ml_runs` スキーマ / Tier B adapter に一切触れていない。

### 6列の置き場（SDK 1.163.0 の実 API で確認・2026-08-02）

`log_params` / `log_metrics` は `Dict[str, float | int | str]` しか受けず、
**型は実行時に検査される**（`ExperimentRun.log_params` は非対応型に `TypeError`）。
確認コマンド: `python -c "import inspect; from google.cloud.aiplatform.metadata import experiment_run_resource as r; print(inspect.getsource(r.ExperimentRun.log_params))"`

| `ml_runs` の列 | Experiments 側 | 比較軸として引けるか |
|---|---|---|
| `status` | `ExperimentRun` の state（`Execution.State.COMPLETE` / `FAILED`） | **○ native** |
| `platform` | params（常に `vertex`） | △ 単一基盤なので軸にならない |
| `stage` | params（文字列） | △ |
| `attempt` | params（int） | △ **採番の正本は Neon** |
| `failure_class` | params（文字列） | △ |
| `write_path` | params（文字列） | △ |

**「格納できるか」は Yes、「5基盤比較の軸として引けるか」は status 以外 No。**

### B（置換）を退けた理由

1. **UC-003「Neon の SELECT だけで5基盤比較」が単一テーブル前提。** Experiments は
   Vertex のサービスで、他4基盤には別物の実験管理がある。置換すると横断集計層を
   **自前で**作ることになり、「自前実装を減らす」動機と正面から矛盾する
2. **`attempt` の採番の正本が動く。** attempt は Neon の同一 (platform, stage) 過去行数 + 1
   （`platforms/shared/contracts/tracking.py:87`）。ここを移すと permission friction
   —— 本ラボ本命の計測 —— が別物になる
3. 上表のとおり、比較6列のうち5列が generic な params にしか入らない

### C（不採用）を退けた理由

Vertex の run だけでも「基盤ネイティブの実験管理がどう見えるか」は本ラボの比較材料であり、
複写のコストは decorator 1枚 + 既定 OFF に収まった。捨てる理由が無い。

## 実装（2026-08-02・main 直コミット）

| ファイル | 役割 |
|---|---|
| `src/platforms/vertex/experiment_sink.py` | `VertexExperimentSink`。`RunSink` を満たす **decorator**。`record_run` は inner の戻り値をそのまま返し、Vertex の run のときだけ Experiments へ複写する |
| `src/platforms/shared/factory.py` | `with_experiment_mirror()` で配線。`MCML_VERTEX_EXPERIMENT` が設定されているときだけ有効（**既定 OFF**） |
| `tests/platforms/test_vertex_experiment_sink.py` | 14 件。守る不変条件は下記 |

### 設計上の要点

- **`next_attempt` は必ず inner へ委譲**する。採番の正本を Neon から動かさない
- **`record_run` の戻り値は inner のもの**。`write_path` の判定を横取りしない
- **Vertex 以外は複写しない**。他基盤を入れると「Experiments に5基盤が揃っている」誤解を生む
- **複写の失敗は呼び出し元へ伝えない**（telemetry は非致命・`docs/06_error_policy.md`）
- `dict` / `list` / `None` / **`bool`** は文字列化してから渡す。`isinstance(True, int)` が真なので
  bool を素通しすると Experiments 側に `1` / `0` で載って読めなくなる
- 既定 OFF にしたのは、有効化がクラウドへの書き込み（＝課金と残留検査の対象）を増やすため

owner 承認のもと GCP 基盤を再構築して実施（apply 18 リソース → イメージ push →
データ配置 → train / register / predict）。**実験行は本番 `ml_runs` に書く**判断。

### 確認できたこと

| 項目 | 結果 |
|---|---|
| Experiments への複写 | ✅ `register-872fe0de…`（state=3 COMPLETE）/ `predict-b3d68273…`（state=4 **FAILED**） |
| 6列が params に載る | ✅ `stage` `attempt` `write_path` `failure_class`（失敗時 `sdk`）`code_revision` |
| `status` が native | ✅ `Execution.State` の COMPLETE / FAILED に落ちた |

### 実装の欠陥を2件検出して修正した

1. **実験が未作成だと複写できない**（commit `98ac402`）。`ExperimentRun.create` は
   `_get_experiment()` を呼ぶだけで作らない。`get_or_create` を前段に入れた
2. **decorator が `merge_run_params` を中継せず、修正07 の resume を壊していた**。
   `TrackedOperations._merge_job_row_params` は `getattr` で存在を見るだけなので、
   持たない decorator を挟むと**静かに何もせず戻る**。実測では学習成功行が
   `params: {}` のままになり `register` が「再開できる学習成功 run が無い」で停止した。
   中継を実装し、**本物の `_tracked()` 経路を通る回帰テスト**を追加

### 設計上の制約（実測で判明・仕様として残す）

**train の成功行は Experiments に載らない。** 学習成功行はジョブ側が書く規約
（`job_owns_success=True` → `RecordingSink` が成功を抑制）なので、
orchestrator の sink decorator を通らない。実測でも Experiments に register / predict は
現れたが train は現れなかった。

つまり複写の対象は **train 失敗・register・deploy・predict** で、
**最も情報量の多い「学習成功行（metrics 付き）」は Neon にしか無い**。
A（併存）の価値が想定より小さいことを意味するので、扱いは owner 判断（下記）。

### 再設計の経緯（2026-08-02・owner 指摘を2度受けて最終形へ）

実装は3段階で作り直した。**第2段も間違っていた**ことを含めて記録する。

| 段階 | 形 | 何が誤りだったか |
|---|---|---|
| 1. sink decorator | 記録経路に複写を挟む | 学習成功行が複写されない（抑制の下流）＋ `merge_run_params` を落として再開を壊した |
| 2. core に `RunObserver` Protocol + 共通層フック | 記録と観測の分離自体は正しい | **実装が1つしか無い抽象を core に置いた。** `ports.py` の「5基盤ぶんの実装が並ぶものだけ port にする」への違反。ML コード側の都合（複写の仕組み）から考え、**5つのインフラから共通層を導く**という向きが逆だった |
| 3. **最終形: `VertexAdapter._tracked` の override** | 単一基盤の関心はその基盤の adapter に閉じる | — |

最終形の構成:
- 有効化は `VertexConfig.experiment`（env なら `MCML_VERTEX_EXPERIMENT` ——
  既存の `MCML_<PLATFORM>_<FIELD>` 解決規約そのもの。factory が独自に env を読む形も廃止）
- 共通層（`core/` / `TrackedOperations` / factory）は Experiments を**一切知らない**。
  これを `test_common_layers_do_not_know_the_observer` が機械的に守る
- 学習成功行も観測される（super() の戻り値は抑制と無関係に手元にある）

### 仕様適合の再検証（2026-08-02・owner「本当に仕様を満たしているか不安」を受けて）

**破れていた。** 比較クエリは teardown しか除外しておらず、再構築検証の run

friction・所要・到達経路・残留の全クエリに混入していた。`ml_runs` は追記専用なので、
campaign 後に run を流すたびに UC-003 / G3「クエリをそのまま流せば再現できる」が壊れる構造。

対処: **比較母集団の定義を計測の正本（sql/schema.sql）に置いた。**
`baseline_runs` / `baseline_infra_events` view（境界 = 2026-08-01 15:00 UTC。
baseline 最終行 12:03Z と最初の campaign 後 run 17:17Z の間、実測の事実）。
比較クエリは生テーブルを読まない（`test_queries_read_only_the_baseline_views` が守る）。

再検証結果: view 経由でクエリをそのまま流し、**failure_class 内訳が親調査 §0 の記録
（sdk 12 / container 1 / network 1 / package 1）と完全一致**、RMSE parity も
5基盤 distinct=1 = `0.4368055090296257`。仕様適合を実測で回復した。

### 5基盤への展開（2026-08-02・owner 依頼「vertex から AWS / Azure も対応」）

**Vertex の実装を移植しなかった。** 導出順序どおり各基盤の制約を先に実測したところ、
「実験追跡」は5基盤で**形そのものが違う**と分かったため。

実測（installed SDK の service model / signature）:

| 基盤 | 実験の口 | 形 | 学習以外 |
|---|---|---|---|
| Vertex | `ExperimentRun.create` | 事後 API | 載る |
| SageMaker | `CreateTrainingJob.ExperimentConfig` | **投入時パラメータ** | **載らない**（`CreateModel` / `CreateEndpoint` / `CreateModelPackage` に口が無いことを boto3 の service model で確認） |
| Azure ML | `command(experiment_name=...)` | 投入時パラメータ | 載らない（job 単位） |
| Databricks | MLflow のワークスペースパス | 基盤内蔵 | ジョブ単位 |
| Snowflake | **無い** | — | — |

したがって Vertex の observer（事後複写）を AWS / Azure へコピーするのは**誤り**。
コピーすると `ExperimentConfig` を使わない別経路ができ、「SageMaker Experiments に
載せた」が嘘になる。実装は各基盤の制約に従った:

- **SageMaker**: `SageMakerConfig.experiment` を追加し、`create_training_job` の
  `ExperimentConfig` に載せた（事後 API は生やさない）。既定 OFF
- **Azure ML**: **既に `experiment_name` を渡していた**（＝ネイティブ対応済み）。
  フィールド名だけ `experiment` に揃え、5基盤で同じ env 規約で上書きできるようにした
- **Databricks**: 同上（`experiment_name` → `experiment`）。実体は MLflow パスのまま
- **Snowflake**: **フィールドを置かない**。他4基盤に揃えて空フィールドを生やすと
  「あるが未設定」に見え、比較レポートで「設定すれば使える」と誤読される

既定値の差も揃えていない —— Vertex / SageMaker は OFF を選べるが、
Azure / Databricks は「実験に属さない」状態が存在しない。**揃えると嘘になる。**

番人: `tests/platforms/test_experiment_tracking_asymmetry.py`（13件）が
フィールド名の統一・既定値の差・Snowflake の不在・observer が他基盤へ移植されないこと・
SageMaker が投入時に載せること（未設定なら送らないこと）を固定する。
