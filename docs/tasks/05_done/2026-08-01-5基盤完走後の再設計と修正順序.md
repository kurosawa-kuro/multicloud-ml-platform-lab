## 1. ゴール再設計 — 最終的にどうあるべきか

実測を踏まえて先に固定する。以降の課題はすべてこのゴールとの差分として書く。

### G1. 比較の再現が「1コマンド + outputs」で閉じる

現状は runbook の本文を読まないと再現できない。`TF_VAR_*` を 10 種類以上手で
export し（§2.2）、**データとイメージの配布は3基盤とも手打ち**（§2.3）。

あるべき姿: 基盤固有の値はすべて `env/config.yaml`（人が決める値）か
`artifacts/*.outputs.json`（apply が決める値）か Doppler（秘密）に入り、
**配布は実装済みの `ArtifactStore` を経由する1コマンド**になり、
runbook は「なぜそうするか」だけを持つ。

### G2. 設定が効かないときは黙って落ちず、失敗する

現状 `common.use_spot: true` は Vertex と SageMaker にしか効かず（§2.1）、
Databricks の wheel 名はバージョン込みで2箇所にハードコードされている（§2.4）。
どちらも**ずれても誰も警告しない**。

あるべき姿: 共通設定は「5基盤に効く」か「効かない基盤を明示列挙して落とす」かの
どちらか。同じ値を2箇所に書く構造を無くす。

### G3. 計測の正本（SQL）が正しい数字を返す

現状 `sql/comparison_queries.sql` の permission friction と stage 別所要は
**teardown 行の混入で汚れている**（§3.1。teardown は `stage=deploy` で記録される）。
要件 UC-003「Neon の SELECT だけで比較ができる」が成立しておらず、
レポートの一部の数字は**手で分離して書いた**（規約「手で数えた値を書かない」違反）。

あるべき姿: クエリをそのまま流せばレポートの表がすべて再現できる。

### G4. metric parity がテストで守られる

現状 `test_metric_parity.py` / `test_code_revision_parity.py` は
**「Phase 0 未着手」を理由に skip されたまま**（§3.2）。
5基盤で一致したという本プロジェクト最大の成果が、回帰テストで守られていない。

あるべき姿: 実測値が入った今、parity テストが `make test` の既定ゲートとして動く。

### G5. ステージを跨いで再開できる

現状 `model_artifact_uri` / `model_version` は Neon に残らず（**5基盤とも
`params={}`**・§3.3）、`resume` は URI を手で発掘しないと使えない。
Azure では回避手段が無く train からやり直した。

あるべき姿: `ml_runs` に stage 間の受け渡し値が残り、
`run_phase.py <platform> resume` が**引数なしで**動く。

### G6. collected は「劣化」ではなく「設計」として扱う

Databricks（psycopg 不在）と Snowflake（EAI がトライアル不可）の collected は
**契約・実行環境の制約**であって実装の不備ではない。しかし現状は fallback 扱いで、
`make collect` の手動実行に依存し、SageMaker では JSONL が `model.tar.gz` の中に
固められて回収に展開が要る（`動作検証-sagemaker.md §4`）。

あるべき姿: direct / collected を対等な2経路として実装し、
**回収まで `phase-train` の中で閉じる**。

### G7. 撤退が IaC で閉じ、閉じない部分は検査が正しく報告する

Azure だけ IaC 管理外の自動生成リソースが RG 削除を阻害し手作業が要った。
かつ `check_residual.py` は完全撤収後に動かない（§3.4）。

あるべき姿: destroy が1コマンドで閉じるか、閉じない残留を
`check_residual.py` が「不明（ERROR）」ではなく正しい分類で列挙する。

## 2. Infra の課題

### 2.1 `common.use_spot` が2基盤にしか効かない — **両方**

**根拠**: `env/config.yaml:32` に `common.use_spot: true`。
`platforms/config.py:200` の `_resolve()` は
`allowed = {f.name for f in fields(...)}` で **dataclass に無いキーを黙って捨てる**。
dataclass fields の実測:

| | `use_spot` | Spot の実制御 |
|---|---|---|
| vertex | あり（`vertex/adapter.py:62`） | adapter（`scheduling_strategy=SPOT`） |
| sagemaker | あり（`sagemaker/adapter.py:84`） | adapter（`EnableManagedSpotTraining`） |
| **azureml** | **無し** | **Terraform 変数** `infra/modules/azure/variables.tf:86`（`vm_priority`） |
| databricks / snowflake | 無し | 概念が無い（serverless / warehouse） |

**Spot の指定が Core（config.yaml → adapter）と Infra（TF 変数 → compute cluster）の
2系統に割れており、Azure だけ Terraform を編集しないと切り替わらない。**
Azure の LowPriority quota 問題（`04_azureml.md`「第2の壁」）で、この二重化のせいで
「config は spot=true なのに落ちるのは TF 側」という切り分けを実際にやった。

### 2.2 `TF_VAR_*` が 10 種類以上、runbook の本文にしか存在しない — **Infra**

**根拠**（`grep TF_VAR_ docs/runbooks/ Makefile`）:

| 基盤 | 手渡し変数 | 分類（H-4 の仮説） |
|---|---|---|
| Databricks | `job_principal` / `create_catalog` / `catalog_name` / `schema_name`（4つ渡さないと ① で落ちる。`動作検証-databricks.md:132`） | config.yaml |
| Snowflake | `create_neon_secret` / `grant_to_user` / `serving_model_version` / **`neon_secret_string`** | config.yaml ×3 / **Doppler** ×1 |
| Azure / SageMaker | `budget_notification_email` | Doppler（メールは個人情報扱い） |
| Vertex | `vertex_submitter_email` | Doppler 同上 |

これらは `env/config.yaml` にも Doppler にも無く、**再現性が runbook の読解に依存**。
`platforms/shared/config.py` は「値の出所を2系統に分ける」ことを目的に掲げているのに、
**Terraform 入力側だけが第3の出所（シェルの export）に取り残されている**。

### 2.3 配布（データ・イメージ）が3基盤とも手打ちで、実装済みの port が死蔵 — **両方**

**根拠**: `platforms/shared/artifacts.py` に `GcsArtifactStore` / `S3ArtifactStore` /
`BlobArtifactStore` が実装・テスト済み（`tests/test_artifacts.py`）。しかし
呼び出し箇所を grep すると **`train_pipeline.py` のコメント3行だけで、
実行経路のどこからも呼ばれていない**。runbook 側の実態:

- `動作検証-sagemaker.md §3`: 「**`S3ArtifactStore` は実装済みだが CLI から呼ぶ口が
  無いので、配布は手打ち**」と自認。しかも serving イメージは
  `docker buildx --oci-mediatypes=false` の特殊手順（OCI index を CreateModel が拒否）
- `動作検証-azureml.md §3`: `az storage blob upload-batch` 手打ち + RBAC 追加が必要
- `動作検証-vertex.md`: 同様に手打ち

**port を切ったのに配線しなかった**分類の課題で、G1 の最大の欠落点。
（Tier B の2基盤は adapter 内に upload 実装があり配線済み——非対称はここにもある。）

### 2.4 Databricks の wheel 名がバージョン込みで2箇所にハードコード — **両方**

**根拠**:

```
env/config.yaml:76                  wheel_filename: multicloud_ml_platform_lab-0.1.0-py3-none-any.whl
infra/modules/databricks/main.tf:36 wheel_path = ".../dist/multicloud_ml_platform_lab-0.1.0-py3-none-any.whl"
```

pyproject の `version` を上げた瞬間、**両方を同時に直さないと
「entry point を引けない」形で実行時に壊れる**（config.yaml:75 のコメント自身が
「ずれると引けない」と警告している）。バージョンは pyproject が正本のはずで、
そこから導出すべき値が2箇所に複製されている。G2 の Tier B 版。

### 2.5 tfstate backend が3方式・Tier B 2基盤が GCP に相乗り — **Infra**

**根拠**（`infra/environments/*/backend.tf`）:

```
gcp-dev / dbx-dev / sf-dev   backend "gcs"  bucket = example-gcp-project-tfstate  ← 3環境が同居
aws-dev                      backend "s3"
azure-dev                    backend "azurerm"
```

**Databricks と Snowflake の state が GCP プロジェクトの生存に依存する。**
GCP を畳むと2基盤の state を失い、「基盤を独立に畳める」前提が崩れている。
加えて state 置き場の bootstrap は3方式とも手作業
（`動作検証-azureml.md §0(b)` / `動作検証-sagemaker.md §2` は chicken-and-egg を
runbook で解いている）。

### 2.6 予算アラートが5基盤とも「実装済みだが既定で無効」 — **Infra**

**根拠**: 5モジュール全部に budget 相当があるが、
`count = var.budget_notification_email == "" ? 0 : 1`
（`aws/main.tf:355` / `azure/main.tf:193`）で**メール未指定なら黙って作られない**。
実害の実測: Azure Phase 4 の初回 apply は `budget_enabled = false` のまま
常時課金エンドポイントを立て、しかも PAYG 化で `spendingLimit=Off` だったため
**ガードレールゼロの時間帯が実在した**（`動作検証-azureml.md §9 段階3`）。
「無いなら失敗する」ではなく「無いなら黙って作らない」になっているのが問題。

### 2.7 クレデンシャルの経路が4系統に割れ、CI 再現性が無い — **Infra**

**根拠**: `docs/runbooks/credentials.md`。

| 基盤 | 経路 | CI で再現できるか |
|---|---|---|
| Vertex | gcloud ADC（CLI ログイン） | ❌ |
| SageMaker | Doppler 静的キー（root キーのまま・意図的、decision-log 記録済み） | ✅ |
| Azure | `az login` + SP 変数 | ❌（SP に寄せれば可） |
| Databricks | Doppler の PAT（**期限 2026-10-30 = 実行可能期限そのもの**） | ✅（期限まで） |
| Snowflake | キーペア `.p8` + Doppler | ✅ |

「同一手順で5基盤を回す」前提が資格情報層で崩れている。ただし
**root キー最小権限化は個人ラボには過剰として対応しない**（owner 判断済み・再提案しない）。
ここでの課題は権限の強さではなく**経路の不統一**。

### 2.8 apply の非対話経路が基盤ごとにバラバラ — **Infra**

**根拠**: `scripts/run_terraform.py:14` は意図的に `-auto-approve` を付けない
（plan-first 原則。これ自体は維持する）。回避策の「保存済み plan を渡す」は
`parse_known_args` で実装済みだが、**runbook に書いてあるのは Azure と Databricks だけ**。
TTY 無しで素の `make tf-apply` を叩くと `EOF` で落ち、
**`infra_events` に偽の failure 行が残る**（2026-08-01 に実際に発生し、
`04_azureml.md` 付録に除外注記を書く羽目になった）。手順の不統一が計測を汚した実例。

## 3. Core の課題

### 3.1 比較クエリの正本が teardown 混入で汚れている — **Core**

**本調査の最重要発見。** 根拠を3点セットで示す。

(1) `core/telemetry/schemas.py:39` の `Stage` は
`train / register / deploy / predict` の4値のみ。teardown が無い。

(2) そのため `vertex/adapter.py:288` と `azureml/adapter.py:335` は teardown を
`self._tracked(Stage.DEPLOY, {"action": "teardown"}, ...)` で記録する。
**attempt カウンタも `(platform, deploy)` を共有**するので、Neon の実データは:

```
azureml deploy   success n=4   ← 実体は deploy 2 + teardown 2（attempt=2,4 が teardown）
```

(3) `sql/comparison_queries.sql` への波及:

| クエリ | 汚染 |
|---|---|
| 2. permission friction（**本命**） | `attempts_until_success` の deploy 行に teardown の成功 attempt が混入しうる。attempt の連番自体が deploy/teardown で混ざっているため「何回で通ったか」の意味が濁る |
| 3. stage 別所要 | deploy の `avg_seconds` に teardown（332〜335s）が算入される |
| 補助（write_path 内訳） | teardown 行が deploy として数えられる |

`04_azureml.md` の「teardown 所要 334.6s / 332.5s」は**手で分離して書いた**。
つまり「手で数えた値をレポートに書かない」（`comparison_queries.sql` 冒頭の規約）に
既に違反した状態で、UC-003（SELECT だけで比較できる）が成立していない。

**修正の2択**（順序は §7 で決める）:
- (a) クエリに `params->>'action' is distinct from 'teardown'` を足す — 軽い・過去データ無修正
- (b) `Stage.TEARDOWN` を追加 — 正攻法だが、**過去行の書き換えは「計測データを消さない」
  規約と衝突する**。新規行のみ新 stage、過去行はクエリで吸収、の併用が現実解（仮説 H-7）

### 3.2 parity テストが skip されたまま — **Core**

**根拠**（`pytest -rs` 実測）:

```

SKIPPED tests/test_metric_parity.py:51,57: Phase 0 未着手
```

機械判定する対象」と宣言しており、**宣言と実態が乖離**。
今 `core/ml` を壊しても `make test` は緑のまま。

### 3.3 stage 間の受け渡し値が Neon に残らない — **Core**

**根拠**: `platforms/shared/contracts/tracking.py:157` `artifact_uri_from()` は
`train_run.params["model_artifact_uri"]` を読む。しかし `:112` の
`job_owns_success=True` により train の成功行は**ジョブ側**
（`platforms/neon/job_record.py`）が書き、ジョブ側は URI を知らない。実測:

```sql
select platform, params from ml_runs where stage='train' and status='success';
-- 5基盤すべて params = {}
```

**道具は既に揃っている**ことに注意——`run_phase.py` には `resume` step-set と
`--artifact-uri` / `--model-version` 引数があり、`factory.deploy_reference()` は
`model_ref` の明示指定を受ける。**欠けているのは「渡す値の永続化」だけ**。
Azure で register/deploy を単体実行できず train からやり直した実害の根因はここ
（`04_azureml.md`「詰まった点 (2)」）。

### 3.4 `check_residual.py` が完全撤収後に動かない — **Core**

**根拠**: Azure ⑦ で実測。RG 削除後に実行すると
`ResourceGroupNotFound` / `ParentResourceNotFound` を **ERROR（残留の有無が不明）**
として返す。「親が消えている」は**残留 0 件の最も確実な証拠**なのに不明扱い——
`residual-resources.md` の判定原理（ERROR を WARN に丸めない・調べられなかったと
無かったは別）の裏返しとして、「確実に無い」を「不明」に丸めている。

### 3.5 train/serve skew のテストが实クラウドのレイアウトを1基盤分しか持たない — **Core**

**根拠**: Azure の「モデルが1段深くマウントされる」skew は実クラウドで初めて発覚し
（`/health` 200 / `/score` 500・`04_azureml.md`「詰まった点 (3)」）、
`locate_model_file()` で解消済み。ただし `tests/test_predictor.py` にあるのは
Azure の1段掘りケースだけで、**SageMaker（`/opt/ml/model` 直下 + `model.tar.gz` 展開後）/
Vertex（シムが `MODEL_DIR` を直接指す）の実レイアウトを模したフィクスチャが無い**。
「5基盤のモデル配置レイアウト」を1つのパラメタライズドテストにすべき。

### 3.6 collected の回収が手動で、置き場も基盤ごとに非対称 — **Core**

**根拠**: `platforms/neon/job_record.py` docstring（Snowflake は sproc_handler が
JSONL を stage へ・常に collected）、`03_databricks.md` ③、
`動作検証-sagemaker.md §4`（**JSONL が `model.tar.gz` に固められ、展開してから
`make collect`**）。3様の回収手順が全部 runbook 頼み。G6 のとおり
`phase-train` の後段に回収を組み込み、「collected でも1コマンドで ml_runs が揃う」に。

## 4. Tier 別に再設計が要る要素

### Tier A（Vertex / SageMaker / Azure ML）

| # | 事情 | 影響 | 区分 |
|---|---|---|---|
| A-1 | モデル受け渡し契約が3者3様（環境変数 / 固定パス / マウント宣言）。`predictor.py` の `resolve_model_dir()` + `locate_model_file()` が吸収 | 基盤を足すたびに分岐が伸びる。**§3.5 のとおりテストが実レイアウトを覆っていない**のが当面の穴 | Core |
| A-2 | **Endpoint 常時課金 + deploy/teardown が支配的**（deploy 513〜547s・teardown 332〜335s vs 学習約4分） | 実験1回の実時間とコストがデプロイに支配される。マネージド実験管理へ移す動機の実測的根拠 | 両方 |
| A-3 | Spot 可否が契約プランに依存（Azure `TotalLowPriorityCores 0/0` → プラン変更で解錠） | §2.1 の二重化と合わせ、「spot を指定したのに効かない」を明示エラーにしないとコスト比較が黙って壊れる | 両方 |
| A-4 | イメージ manifest 形式の非互換（SageMaker CreateModel が OCI index 拒否。**Training は通るので ⑤ まで潜伏**） | `make docker-build` が共通のはずが、serving だけ基盤別ビルドが要る。§2.3 の配布配線に含めて解決 | Infra |

### Tier B（Databricks / Snowflake）

| # | 事情 | 影響 | 区分 |
|---|---|---|---|
| B-1 | **外部 egress が契約段階で切られる**（Snowflake: トライアルは EAI 不可 / Databricks: trusted domains 限定・`Verify identity` で変わる可能性 = H-3） | direct が構造的に取れない。G6（collected を一級市民に）以外の解が無い | Core |

## 5. 次フェーズ — マネージドパイプライン / 実験管理への載せ替え

### 5.1 載せ替えられるか

**仮説（H-1）: Tier A 3基盤とも技術的には載せ替え可能。ただし本ラボの計測粒度が壊れる。**

現在の adapter は `submit → register → deploy → predict` の4操作
（`platforms/shared/contracts/ports.py:38`）で、各基盤のパイプライン
（Vertex AI Pipelines / SageMaker Pipelines / Azure ML Pipelines）のステップに
ほぼ1対1対応する。問題は実行の所有者が移ること:

- `ml_runs` の行は **adapter が能動的に `_tracked()` を呼ぶ**ことで生まれる
  （`contracts/tracking.py:96`）。パイプラインが実行を所有すると、この呼び出し点が
  ステップ内部へ移り、**attempt / failure_class を今の粒度で取れるかが未知**。
- permission friction と stage 別所要は本ラボの本命の計測値。
  これを失う載せ替えは「比較ラボ」としては退行になる。

**確認方法**: Vertex AI Pipelines で1本だけ組み、`ml_runs` に同じ6列
（platform / stage / status / attempt / failure_class / write_path）が埋まるか見る。
埋まらない列が「自前実装でしか測れない値」の実体。

### 5.2 ブランチを切るべきか

**結論: 切る。**

1. 現 main は「5基盤完走」の再現可能な状態で、比較レポートの一次データ
   （`code_revision`）と対応している。ここは壊さない。
2. 載せ替えは `ml_runs` の作られ方を変える可能性が高く（§5.1）、
   粒度の違う行が混ざると `sql/comparison_queries.sql` の5本が意味を失う。
   **§3.1 の教訓そのもの**——記録の意味論を途中で変えると計測の正本が汚れる。

運用ルール「個人開発リポは main 直コミット」との衝突は、
**「main の直コミットは維持しつつ、載せ替え実験だけ長寿命ブランチ」**という
例外として owner が明示合意する（この文書がその合意の場でよい）。

### 5.3 Core は「自前実装」と「マネージド利用」に分離できているか

**結論: 学習・推論ロジックは完全に分離済み。計測ハーネスの3点が自前実行と結合。**

無傷で載る層:
- `core/ml/`（学習）: クラウド SDK を import しない。`test_core_boundaries.py` が pin
- `core/app/serving/`（推論）: 環境変数の吸収だけ。BYOC ならそのまま載る

結合している3点:

| # | 箇所 | 結合の中身 |
|---|---|---|
| C-1 | `contracts/tracking.py:96` `_tracked()` | 「1操作=1行」を **adapter が能動的に書く**前提。マネージド側が実行を所有すると呼び出し点が消える |
| C-2 | 同 `:112` `job_owns_success` | 成功行の所有者は**ジョブ側**という規約（write_path の真値のため）。パイプラインのステップが誰の名前で書くかを決め直す必要 |
| C-3 | `neon/job_record.py` | 学習コンテナの entrypoint シムから CLI として呼ばれる前提。パイプラインステップに同じシムを差し込めるかは未確認（H-2） |

**確認方法（H-2）**: Vertex AI Pipelines のカスタムコンポーネントで既存の学習イメージを
そのまま使い、`python -m platforms.neon.job_record` を同じ引数で呼ぶ。
通れば C-3 の結合は薄く、C-1/C-2 だけがパイプライン側の記録設計の論点になる。

## 6. Core / Infra どちらから着手するか

**結論: 「計測の正本」（Core だが実クラウド不要）→ Infra（再現性）→ Core（実クラウド検証が要るもの）。**

初版は「Infra が先」としたが、再調査で §3.1（比較クエリ汚染）が見つかったため修正する。
判断の構造:

1. **§3.1 と §3.2 は実クラウド不要で、放置すると以降の全作業の判断材料
   （クエリ結果・テスト）が信用できない。** 最優先。
2. Core の残り（§3.3 以降）は検証に実クラウドが要る。その実クラウドを立てる手順が
   runbook 依存（§2.2 / §2.3）なので、**先に Infra で再現性を確保しないと
   Core 修正を検証できない**。
3. Infra の課題は `terraform plan` 差分と `make test` で単独検証できる。
