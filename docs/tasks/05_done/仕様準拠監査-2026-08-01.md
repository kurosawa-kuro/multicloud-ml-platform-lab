## 詳細

### G1: ジョブ内テレメトリ経路が全基盤で未実装（最重要）

仕様: 02「到達経路: **primary = ジョブ内から直接 INSERT** / fallback = JSONL を各基盤ストレージへ出力し
`make collect`」。01「到達可否そのものを比較軸とする（**Tier A=通常egress / Tier B=宣言的な統合オブジェクト経由**）」。
UC-003 / 05 の `write_path`。

実測:

- `core/ml/cli/__main__.py` は track() を一切呼ばない（学習ジョブ内で ml_runs 行が生まれない）。
- `docker/training/Dockerfile:48` は psycopg を入れているが、COPY されるのは `src/core` のみで
  `platforms/neon`（NeonRunSink）が入らない。psycopg は現状デッドウェイト。
- `sproc_handler.py` は成果物 PUT のみ。JSONL を書かない。
- Databricks はジョブ内コードそのものが無い（G2）。
- 現状の ml_runs 記録は **全て adapter 側（オーケストレータのローカルマシン）**の `_tracked()`。
  これで write_path='direct' が付くが、それは**手元マシンの egress** であって基盤の egress ではない。

帰結: 「Tier A=通常 egress / Tier B=統合オブジェクト経由」という到達経路比較軸と
`failure_class='network'`（Snowflake EAI / Databricks serverless egress の失敗計測）が**一度も観測されない**。
Terraform 側は network rule / secret / EAI を作っているのに、それを使う側が居ない。

**採用: 案A（ジョブ内が train 行の正）。** 実装は次のとおり。

- `src/platforms/neon/job_record.py`（新規）: 成果物ディレクトリの `run.json` を読み、
  Neon 直 INSERT を試みて `direct`、届かなければ**成果物と同じ場所へ** JSONL を落として
  `collected`。exit code → failure_class（1=sdk / 2=data / その他=container）。
  **常に exit 0**（telemetry は非致命）。
- 所有者規約: `submit_training` の**成功行はジョブ側**、**投入失敗行は adapter 側**
  （ジョブが起動していないので adapter が唯一の記録者）。
  `TrackedOperations._tracked(..., job_owns_success=True)` で実装し、
  `tests/test_adapter_contract.py` が5基盤ぶん pin。
- run_id / attempt は adapter が発番・解決してジョブへ渡す（Vertex args / SageMaker
  hyperparameters / AzureML command / dbx python_params / sproc payload）。
  attempt を渡すのは、ジョブ側が Neon へ届かない可能性があり**そこで数え直せない**ため。
- Neon 接続情報は `telemetry_env()` が Tier A のジョブ定義 env へ載せる。
  **CODE_REVISION は渡さない**（コンテナに焼き込んだ値と食い違うと同一SHA担保が壊れる）。
- Tier A コンテナに `src/platforms/{__init__.py,neon}` を追加同梱（core 境界は不変。
  core は platforms を import しない）。シム3本が学習の**後**に job_record を呼ぶ。
- Snowflake は warehouse に psycopg が無いため `sproc_handler` が JSONL を stage へ PUT
  （必ず collected）。Databricks は wheel の entry point を
  `platforms.databricks.job_main:main`（cli を回した後に job_record を呼ぶ wrapper）にした。
  serverless に psycopg が無く secret 受け渡しも未配線のため Volume 上の JSONL fallback に
  落ちる（Phase 3 precheck 項目）。**この差自体が比較結果。**

残るリスク: ジョブ側の記録が Neon・JSONL とも失敗した場合、その試行の行は残らない
（成果物 `run.json` だけが証跡）。attempt も進まない。JSONL の書き先は必ず作成済みの
出力ディレクトリなので実現性は低いが、Phase 1 で実測して確認する。

### G2: Databricks の wheel 実行チェーンが断線（4箇所）

仕様: 02 Tier B 契約「Databricks 投入: Jobs API / Python wheel task。同一性: src/core/ml を wheel 化して配布」。

実測の断線点:

1. wheel に entry point が無い。`infra/modules/databricks/variables.tf:92-96` は
   `entry_point="train"`（console_scripts 名）を前提にするが、`pyproject.toml` に
   `[project.scripts]` が無い。
2. `package_name` 既定が `"core"`（variables.tf:86-90）だが、`adapter.build_wheel()` は
   リポジトリルートで `python -m build` するため dist 名は `multicloud_ml_platform_lab`。
   `python_wheel_task.package_name` は dist 名と一致が必要。さらに
   `DatabricksConfig.wheel_filename="core_ml-0.1.0-py3-none-any.whl"` は第3の名前を想定している。
3. `adapter.submit_training()` の `run_now(python_params=["--params", ...])`
   （adapter.py:176-180）は cli 契約（`--input` `--output` 必須）を満たさない。
   仮に entry point が cli でも exit 2 で即死する。
4. `model_artifact_uri_for(remote_run_id)`（adapter.py:301-303）は
   `runs/<Databricks run_id>/model` を成果物の場所と主張するが、ジョブ側に
   その場所へ書く仕組みが無い（remote_run_id は完了後にしか分からない）。

**修正済み（4点とも）**:

1. `pyproject.toml` に `[build-system]` と
   `[project.scripts] train = "platforms.databricks.job_main:main"` を追加
   （cli 直ではなく wrapper。学習後にジョブ内から ml_runs を記録するため —— core は
   platforms を import できないので cli 自身に記録は入れられない。見直し2回目で修正）。
2. dist 名を `multicloud_ml_platform_lab` に統一（Terraform `job_package_name` /
   `wheel_path` / `config.yaml` / `DatabricksConfig.wheel_filename`）。
   `tests/test_packaging_contract.py` が4箇所の一致を pin。
3. `python_params` を Tier A のシムと同じ形へ（`--input` / `--output` / `--params` / `--run-id`）。
   入出力は UC Volume の通常パス。
4. 成果物 URI を `ctx.run_id` 基準へ（Databricks 側 run_id 依存を廃止）。

加えて `require_code_revision_stamp()` を追加し、**stamp 忘れをビルド前に止める**
（wheel / zip には .git も CODE_REVISION も無く、忘れるとジョブ起動後に落ちる）。
Snowflake 側は stage zip を作る手段自体が無かったので `SnowflakeAdapter.build_package()`
と `make sf-package` を追加。

実測検証: `python -m build --wheel` → `multicloud_ml_platform_lab-0.1.0-py3-none-any.whl`。
`entry_points.txt` に `train = platforms.databricks.job_main:main`、`top_level.txt` に
core / platforms、`core/ml/config/_stamp.py` と `platforms/databricks/job_main.py` の同梱を確認。
stage zip は 52 ファイルで他基盤 adapter を含まない。

### G3: Tier A serving イメージ未実装

仕様: 02「推論側は1イメージで3契約」。`core/app` は実装・テスト済みだが、
`docker/` には `training/` しか無く、**serving を配布する手段が無い**。
さらに `predictor.py:12-17` が契約として明記する「Vertex 起動シムが gs:// の

`CODE_REVISION` 焼き込み）+ `docker/serving/entrypoint.sh`（SageMaker の `serve` 引数を読み飛ばし、

`docker/serving/fetch_gcs_model.py`（**stdlib のみ**。メタデータサーバのトークン + GCS JSON API。
3基盤共通イメージに GCP SDK を入れないため）+ `make docker-build-serving`。
学習イメージと**同一 minor** の lightgbm / pandas を固定（ずれると同じ model.txt で予測が変わる）。

### G8: Tier B の依存バージョン未固定（metric parity リスク）

01 破綻条件「5基盤で RMSE が不一致 → 実装漏れ」。pyproject は minor pin
（lightgbm>=4.6,<4.7）だが、`snowflake/adapter.py:58-63` の `SPROC_PACKAGES` は
バージョン無指定 = Anaconda channel の最新が入る。channel の lightgbm が 4.6 系でなければ
同一SHAでも RMSE がずれ、原因調査に時間を溶かす。
**修正済み**: `SPROC_PACKAGES` を pyproject と同じ minor に固定
（`lightgbm>=4.6,<4.7` / `scikit-learn>=1.9,<1.10` / `pandas>=2.3,<2.4`）。
`tests/test_snowflake_adapter.py` が pyproject との一致を pin。
channel に該当版が無ければ **`CREATE PROCEDURE` が落ちて即分かる**（RMSE が静かにずれるより良い）。
Phase 5 precheck の項目5に、この pin が入った旨を追記済み。
Databricks 側は G2 の wheel メタデータ pin で担保。

### G9: RandomForest baseline が仕様にあるが未実装

一方 01 は「精度の優劣比較（非対象）」で、baseline の消費者は計測パイプラインに存在しない。

**修正済み（opt-in 実装）**: `core/ml/evaluation/baseline.py` +
`TrainingConfig.with_baseline`（既定 **False**）+ CLI `--with-baseline` + `make BASELINE=1 train`。
用途は精度比較ではなく**健全性チェック**（列の取り違え・目的変数の混入・分割のずれの検出）で、
キーは `baseline_` 接頭辞に分けて比較 SELECT と混ぜない。既定 False なのは、
5基盤のジョブで毎回2モデル学習すると**比較したい実行時間に無関係な負荷**が乗るため。
実測: LightGBM RMSE 0.4368 / RF RMSE 0.5153（健全）。
