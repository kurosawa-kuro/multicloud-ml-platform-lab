# 修正07: stage 間の受け渡し値を Neon に残し、resume を引数なしで動かす

Weight Class: **Heavy**（Neon への書き込み内容の変更 + 実クラウド検証が必須）
親調査: [2026-08-01-5基盤完走後の再設計と修正順序.md](./2026-08-01-5基盤完走後の再設計と修正順序.md) §3.3 / G5 / 順序#7
着手条件: 修正01〜06 完了後（検証手段と再現性がそれで揃う）

## Goal

`ml_runs` の train 成功行に `model_artifact_uri`、register 成功行に `model_version` を残し、
`run_phase.py <platform> resume` が**引数なしで**（Neon から直近成功を引いて）動く。

## Value

dev speed / cost。現状は中断すると train からやり直し（Azure で実害・deploy 5〜9分が再課金）。
CLI（`--artifact-uri` / `--model-version`）と `deploy_reference()` は実装済みで、
**欠けているのは値の永続化だけ**（5基盤とも `params={}` を実測確認済み）。

## Scope

- `platforms/neon/job_record.py` に `--model-artifact-uri` 引数を追加し、
  ジョブ側が書く成功行の params に載せる（Tier A シム3本の引き渡しを含む）
- register の成功行に `model_version` / `model_resource_name` を残す（adapter 側）
- `run_phase.py resume` に「引数省略時は Neon から直近成功の値を引く」解決を追加
- 実クラウド検証: 最低1基盤（Azure が本命 —— 実害が出た基盤）で
  `train → 中断 → resume` を通す

## Non-scope

- 過去行への値の埋め戻し（しない）
- パイプライン化（修正10）

## Risk

- ジョブ→Neon の書き込み内容が変わる。job_record は「telemetry 非致命」契約なので
  失敗しても学習は落ちないが、**引数の増加がシム3本すべてに波及**する
  （entrypoint_vertex / sagemaker / azureml.sh）。1本でも渡し忘れると
  その基盤だけ resume 不能になり、気づきにくい
- resume の「直近成功を引く」が**別の実験の成果物を掴む**危険。
  code_revision の一致を条件に入れる

## Change Condition

シム3本と adapter 5本の変更は、fake での契約テスト（値が params に載る）を先に通してから。

## Done Condition

実クラウドで `phase-train` → プロセス終了 → `run_phase.py <p> resume`（引数なし）が
register/deploy/predict を完走し、`ml_runs` に新しい成功行が揃う。最低1基盤で実測。

## Owner-only Decisions

- 実クラウド検証をどの基盤で何回やるか（コストが出る。Azure 1回 + Vertex 1回を提案）
- resume が引く「直近成功」の定義（code_revision 一致を必須にするか）

## Capability Boundary

- Neon: `ml_runs` への INSERT 内容の変更（スキーマ変更なし・params JSONB 内のキー追加のみ）
- クラウド: dev リソースの一時作成（検証後 teardown + destroy）

## Allowed Paths

`src/platforms/**` / `scripts/run_phase.py` / `docker/training/entrypoint_*.sh` /
`tests/**` / `docs/runbooks/**`（手順更新）

## Forbidden Paths

`sql/schema.sql`（スキーマ変更はこのタスクに含めない）/ `infra/**`

## Rollback Trigger

- 検証で「別実験の成果物を掴む」ケースが1度でも出たら、引数なし resume を封印し
  明示引数必須へ戻す（永続化だけ残す）

## Evidence Required

Level 4（実クラウド実測）: resume 完走時の `ml_runs` SELECT 結果と
実行ログを本タスクに貼る。

## 実施結果（2026-08-01・Evidence Level 4）

### 実装

| 変更 | 内容 |
|---|---|
| `platforms/neon/run_sink.py` | `merge_run_params()` を追加。**UPDATE 専用**（`_MERGE_PARAMS_SQL`）。upsert にすると、ジョブが Neon へ届かなかったとき adapter が行を作り `write_path='direct'` を騙るため |
| `platforms/shared/contracts/tracking.py` | `job_owns_success` の成功時に adapter 側 params を追記。telemetry 非致命（失敗しても adapter の結果を変えない） |
| `platforms/shared/resume.py` | 新規。直近の成功 run から値を引く + **`src/core/ml` の tree hash** で互換性を判定 |
| `scripts/run_phase.py` | `resolve_resume_values()`。明示指定が常に勝つ |

**シム3本の変更は不要だった。** 当初は `job_record.py` に `--model-artifact-uri` を足す計画だったが、
ジョブは自分の成果物がどの URI で参照されるかを知らない（Azure の URI は
サービスが採番したジョブ名に依存する）。adapter 側からの追記で解決した。

### 実クラウド検証（Azure ML）

学習だけ実行して**プロセスを終了**させ、別プロセスで引数なし `resume`:

```
-- 再開元 train run=c8a1a49a-59ca-407c-be42-a2d04271e02d
   artifact=azureml://jobs/heroic_pizza_q42zjqtbx0/outputs/model
[success] azureml    register  attempt=4   7.3s
[success] azureml    deploy    attempt=5 543.8s
[success] azureml    predict   attempt=3   1.2s
-- 3 stage 実行 / 失敗 0
```

`ml_runs` の実データ（**過去行は書き換えていない**）:

```
attempt=4 11:39  params={"job_name": "heroic_pizza_q42zjqtbx0",
                         "model_artifact_uri": "azureml://jobs/.../outputs/model"}
attempt=3 08:12  params={}
attempt=2 07:48  params={}
```

予測値 `4.183217948107466`（5基盤一致値と同じ）。**中断コストが全 stage → 1 stage に下がった。**

### 途中で見つけて直したもの（修正04 の積み残し）

素の `terraform plan` は config.yaml / Doppler 由来の `-var` を受け取らず、
**変数の抜けた plan が保存されて apply がそれを適用していた**
（`Plan: 9 to add` = 予算アラート欠落。正しくは 10）。
`run_terraform.py` に `plan` アクションを追加し、5 runbook を更新。
plan は `infra_events` に記録しない（試行回数を水増ししない）。

### Rollback Trigger の判定

「別実験の成果物を掴む」ケースは発生しなかった。tree hash 判定が働いており、
判定不能時も「一致した」に倒さず拒否する（テストで固定）。**引数なし resume を維持する。**

### 残した制約

collected 経路（Tier B）は行が `make collect` の後に現れるため、この時点では追記が
0 件になる。Tier B の resume は `--artifact-uri` の明示指定が要る。
