# 修正02: 比較クエリの teardown 混入を分離する（計測の正本の修復）

Weight Class: Standard（SQL + enum 追加。ただし Neon の制約変更を含む場合は owner 確認）
親調査: [2026-08-01-5基盤完走後の再設計と修正順序.md](./2026-08-01-5基盤完走後の再設計と修正順序.md) §3.1 / G3 / 順序#2

## Goal

teardown（現在 `stage=deploy` + `params.action='teardown'` で記録）が
`sql/comparison_queries.sql` の permission friction / stage 別所要 / write_path 内訳を
汚さない状態にする。UC-003「Neon の SELECT だけで比較ができる」を回復する。

## Value

collection accuracy / integrity。本命クエリ（permission friction）の
deploy 行に teardown の attempt・所要が混ざっており、
レポートの一部数字が手作業の分離でしか出せない（規約違反状態）。

## Context

実データ: azureml の「deploy success n=4」は実体 deploy 2 + teardown 2
（attempt=2,4 が teardown）。attempt カウンタが `(platform, deploy)` を共有している。
`core/telemetry/schemas.py:39` の `Stage` は4値のみ。

## Scope

- 第1段: `comparison_queries.sql` の該当クエリに
  `params->>'action' is distinct from 'teardown'` の除外を追加（過去データ無修正で効く）
- 第2段: `Stage.TEARDOWN` を enum に追加し、**新規行のみ**新 stage で記録
  （`vertex/adapter.py` / `azureml/adapter.py` の `_tracked(Stage.DEPLOY, {"action": ...})` を変更）
- `tests/test_sql_contracts.py` に新旧両形式を読めるテストを追加（親調査 H-7）

## Non-scope

- **過去行の UPDATE はしない**（「計測データを消さない」規約。旧形式はクエリで吸収し続ける）
- teardown の attempt 採番の過去分の振り直し

## Plan

1. `sql/schema.sql` の stage が CHECK 制約 / enum かを確認（Neon 側の変更要否が決まる）
2. クエリ側の除外を先に入れ、既存データで再実行して数字が変わることを確認
3. `Stage.TEARDOWN` 追加 + adapter 2箇所の変更 + テスト
4. `04_azureml.md` の「手で分離した」注記を「クエリで再現可能」に更新

## Acceptance Criteria

- [ ] クエリ2/3/補助を流した結果に teardown 行が混入しない（旧形式データで確認）
- [ ] 新規 teardown が `stage='teardown'` で記録される（fake sink テスト）
- [ ] `make test` green

## Stop / Ask Owner If

- Neon の `ml_runs` に stage の CHECK 制約があり **ALTER が必要**な場合（本番 DB 変更 = owner 承認）
- 除外を入れた結果、既発行レポートの数字と食い違いが出た場合（レポート側の訂正判断は owner）
