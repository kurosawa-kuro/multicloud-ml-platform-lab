# 修正09: tfstate の独立化 + 予算アラートの既定有効化

Weight Class: **Heavy**（state 移動 = 最も血が出やすい構造変更。apply/destroy を伴う）
親調査: [2026-08-01-5基盤完走後の再設計と修正順序.md](./2026-08-01-5基盤完走後の再設計と修正順序.md) §2.5 §2.6 / G7 / 順序#9
着手条件: 修正01〜08 完了後（再構築の検証コストが下がってから）

## Goal

1. `dbx-dev` / `sf-dev` の tfstate を GCS（`example-gcp-project-tfstate`）相乗りから外し、
   **GCP を畳んでも Tier B 2基盤の state が生きる**構成にする。
   state 置き場の bootstrap を IaC（または冪等スクリプト）にする
2. 予算アラートを「メール未指定なら黙って作らない」から
   「**メールが解決できなければ apply を失敗させる**」に変える（5 module）

## Value

safety / integrity。(1) は「基盤を独立に畳める」前提の回復。
(2) は Azure で実在した「ガードレールゼロで常時課金リソースが立つ」時間帯の再発防止。

## Scope

- backend 設計の決定（案: Tier B も各基盤側 or 中立の1箇所。トレードオフを提示して owner 決定）
- `terraform init -migrate-state` による state 移動（2環境）
- bootstrap（バケット/コンテナ作成）の冪等スクリプト化
- 予算: `variable "budget_notification_email" { validation { ... } }` 等で必須化。
  値は修正04 の経路（Doppler）から供給

## Non-scope

- gcp-dev / aws-dev / azure-dev の backend 変更（動いているものは動かさない）
- 予算金額の変更（¥2,000/月のまま）

## Risk

- **state 移動の失敗 = 実リソースとの対応喪失**。現在5基盤とも destroy 済み
  （残るは tfstate 用リソースのみ）なので、実は**いまが最も安全な移動時期**。
  ただし state には過去の outputs が残っており、消すと `artifacts/*.outputs.json` の
  再生成経路も失う
- 予算必須化は「メール未設定で apply が通らない」を全環境に導入する = 摩擦の追加。
  修正04 が先に済んでいれば Doppler から自動供給されるので摩擦は出ない（依存関係）

## Change Condition

移動前に両環境の state をローカルへ `terraform state pull` でバックアップし、
移動後の `terraform plan` が **no changes** であることを確認してから次へ進む。

## Done Condition

- 2環境の backend が GCP 非依存で、`terraform plan` no changes
- 5環境すべてで「メール未解決の apply」が plan/validate 段階で落ちる
- bootstrap がスクリプト1本（実行済み環境では冪等に no-op）

## Owner-only Decisions

- Tier B state の行き先（各基盤側 / 中立ストレージ。コストと依存の対トレード）
- 予算必須化を5環境同時にやるか段階導入か

## Capability Boundary

- terraform state の pull / migrate（破壊的になりうる）
- クラウド: state 用ストレージの新規作成（実質無料レンジ）

## Allowed Paths

`infra/**` / `scripts/**` / `docs/runbooks/**` / `Makefile`

## Forbidden Paths

`src/**`（このタスクで Core は触らない）

## Rollback Trigger

- migrate 後の plan が差分を出したら即中断し、pull しておいた state へ戻す
- bootstrap スクリプトが既存リソースを置換しようとしたら中断

## Evidence Required

Level 4: 移動前後の `terraform plan` 出力（no changes）と
`state pull` バックアップの保存先を本タスクに記録。

## 実施結果（2026-08-01・Evidence Level 4）

### owner 判断の結果

| 論点 | 決定 |
|---|---|
| Tier B state の行き先 | **Neon の pg backend**（比較対象5基盤のどれにも依存しない中立の置き場） |
| 予算必須化の入れ方 | Doppler 登録を先に、その後 5環境同時 |

### 調査で確定した事実

**Tier B は自前で tfstate を置けない。** UC Volume も Snowflake stage も Terraform
backend ではなく、オブジェクトストレージが外に無い。だから GCS に相乗りしていた。
これは「データが基盤の中にある」という Tier B の性質が **IaC の足場にまで及ぶ**
ということで、比較材料として `selection-checklist.md` に追加した。

### pg backend の実測（先に probe で検証してから本番へ）

Neon 固有の壁が2つあり、どちらも実測で確認した:

| 壁 | 症状 | 対処 |
|---|---|---|
| pooled endpoint | pg backend の state lock がセッションレベル advisory lock を使い、transaction pooling で動かない | `DB_NEON_MULTICLOUD_DIRECT_URI` を使う |
| **SNI 非対応** | `pq: Endpoint ID is not specified...` で init が落ちる | `options=endpoint=<id>` を付与（`scripts/tf_backend.py` が組む） |

probe（`terraform_data` 1個）で apply / destroy / ロックまで通ることを確認してから
本番の backend を切り替えた。

### 移行の実測

```
tfstate_dbx_dev.states  →  [('default', 840)]   ← 書き込み確認済み
tfstate_sf_dev.states   →  []                    ← 未 apply のため空（正常）
```

**「移行」ではなく「切り替え」だった。** 5基盤とも destroy 済みで
state は 0 リソース（182 bytes の空 state）だったため、`-migrate-state` は
コピーするものが無かった。backend が正しく動くことは
`apply -refresh-only` で実書き込みして確認した（840 バytes が Neon に着いた）。

移行前 state はバックアップ済み（resources 0 件 / outputs 0 件が前後で一致）。
lineage だけ空になるが、これは空 state に lineage が無かったため。

### 予算必須化

ガードレールの入口が3通りに分かれていることが分かった:

| 基盤 | 入口 | 対処 |
|---|---|---|
| AWS / Azure | `budget_notification_email` | `validation` で空を拒否 |
| GCP | `billing_account_id` | 同上 + `terraform_vars` で required 化 |
| Snowflake | `create_resource_monitor`（既定 true） | false にするとガードレールが無くなる旨を description に明記 |
| Databricks | **無し**（`databricks_budget` は account-level provider 専用） | Free Edition では作れない。cluster policy が代替 |

5環境とも未解決変数で plan が停止することを実測で確認:

```
gcp-dev    MCML_TF_VERTEX_SUBMITTER_EMAIL
aws-dev    MCML_TF_BUDGET_EMAIL
azure-dev  MCML_TF_BUDGET_EMAIL
dbx-dev    MCML_TF_DBX_JOB_PRINCIPAL
sf-dev     MCML_TF_SF_GRANT_TO_USER
```

### Rollback Trigger の判定

migrate 後の plan が差分を出すケースは発生しなかった（state が空のため plan は
「8 to add」で移行前と同一）。バックアップからの復旧は不要。

### 残した作業（owner 操作）

**Doppler への登録が未了。** 以下4つは値が runbook の export にしか無かったもので、
登録するまで各環境の apply が停止する（**ガードとしては意図どおり**）:

```
MCML_TF_VERTEX_SUBMITTER_EMAIL   MCML_TF_BUDGET_EMAIL
MCML_TF_DBX_JOB_PRINCIPAL        MCML_TF_SF_GRANT_TO_USER
MCML_TF_BILLING_ACCOUNT_ID       （GCP 予算用・今回必須化）
```

**旧 GCS state（`example-gcp-project-tfstate/multicloud-ml-platform-lab/{dbx,sf}-dev`）は
残してある。** 削除は owner 判断（当面はバックアップとして有用）。
