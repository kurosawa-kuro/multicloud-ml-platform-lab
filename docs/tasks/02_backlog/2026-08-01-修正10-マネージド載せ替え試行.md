# 修正10: マネージドパイプラインへの載せ替え試行（Vertex 1本・別ブランチ）

Weight Class: **Heavy**（新アーキテクチャの検証・実クラウド・記録意味論に触れる）
親調査: [2026-08-01-5基盤完走後の再設計と修正順序.md](./2026-08-01-5基盤完走後の再設計と修正順序.md) §5 / H-1 H-2 / 順序#10
着手条件: 修正01〜09 完了後。**長寿命ブランチで行い main に入れない**（§5.2 の owner 合意事項）

## Goal

Vertex AI Pipelines でパイプラインを1本組み、仮説2つを判定する:

- **H-1**: `ml_runs` の6列（platform / stage / status / attempt / failure_class / write_path）が
  マネージド実行でも埋まるか。埋まらない列 = 「自前実装でしか測れない値」の実体
- **H-2**: 既存の学習イメージ + `python -m platforms.neon.job_record` を
  パイプラインのカスタムコンポーネントからそのまま呼べるか（C-3 結合の薄さ判定）

## Value

docs canonicalization（次フェーズの意思決定材料）。
「Tier A をマネージドパイプライン / 実験管理に載せ替えるか」の判断を
推測ではなく実測で下せるようにする。

## Scope

- ブランチ `experiment/vertex-pipelines`（名称は着手時に確定）
- Vertex AI Pipelines のパイプライン定義1本（train → register の2ステップで十分。
  deploy/predict は H-1/H-2 の判定に不要なら省く）
- 判定結果を親調査 §5 に追記し、続行 / 撤退を owner に諮る

## Non-scope

- SageMaker / Azure ML への横展開（Vertex の結果を見てから）
- main への統合・既存 adapter の変更
- マネージド実験管理（Vertex Experiments 等）——パイプラインの結果次第で別タスク

## Risk

- **記録の意味論が壊れる**: パイプライン実行の行が既存 `ml_runs` に混ざると
  比較クエリ5本が濁る（修正02 の教訓）。→ 対策: 実験中は `code_revision` で分離し、
  本番テーブルを汚す場合は実験用 branch DB（Neon branch）を使う
- コスト: Pipelines の実行課金 + 一時リソース。1回の試行は数百円レンジの想定

## Change Condition

ブランチ内で自由。main / 本番 Neon への書き込みだけ上記の分離を守る。

## Done Condition

H-1 / H-2 の判定が「埋まった列 / 埋まらなかった列」の表として親調査に追記され、
続行 or 撤退の owner 判断が decision-log に残る。リソースは destroy 済み。

## Owner-only Decisions

- Neon branch を切るか本番テーブルを code_revision 分離で使うか
- 判定後の続行 / 撤退

## Capability Boundary

- クラウド: Vertex AI Pipelines の実行（GCP・課金あり）
- Neon: 実験行の書き込み（分離策の下で）

## Allowed Paths

ブランチ内は全域可。main には触れない。

## Forbidden Paths

（main 上の）`src/**` / `sql/**` / `docs/comparison/**` — 実験結果の追記は親調査のみ

## Rollback Trigger

- 実験行が本番 `ml_runs` に分離なしで混入したら、即座に該当 code_revision を特定して報告
  （削除するかは owner 判断。「計測データを消さない」規約との調整）

## Evidence Required

Level 4: パイプライン実行の実ログと `ml_runs`（または branch DB）の SELECT 結果。
判定表を親調査 §5 へ。
