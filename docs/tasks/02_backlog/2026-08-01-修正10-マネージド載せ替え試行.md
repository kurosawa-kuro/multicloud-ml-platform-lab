# 修正10: マネージドパイプラインへの載せ替え試行（Vertex 1本・別ブランチ）

Weight Class: **Heavy**（新アーキテクチャの検証・実クラウド・記録意味論に触れる）
親調査: [5基盤完走後の再設計と修正順序](../05_done/2026-08-01-5基盤完走後の再設計と修正順序.md) §5 / H-1 H-2 / 順序#10
着手条件: **満たした**（修正01〜09 は 2026-08-02 に到達を再検証済み）。
ただし Heavy のため **着手前に owner 承認が必要**。承認前にクラウドを叩かない。

## Goal

Vertex AI Pipelines でパイプラインを1本組み、仮説2つを実測で判定する。

- **H-1**: `ml_runs` の6列（platform / stage / status / attempt / failure_class / write_path）が
  マネージド実行でも埋まるか。**埋まらない列 = 「自前実装でしか測れない値」の実体**
- **H-2**: 既存の学習イメージ + `python -m platforms.neon.job_record` を
  パイプラインのカスタムコンポーネントからそのまま呼べるか（C-3 結合の薄さ判定）

判定そのものが成果物であって、載せ替えの完成は Goal ではない。

## Value

docs canonicalization / failure detection。「Tier A をマネージドパイプラインへ載せ替えるか」を
推測ではなく実測で決められるようにする。**載せ替えると本ラボ本命の計測（permission friction・
stage 別所要）を失う可能性がある**ため、判定なしに進めると比較ラボとして退行しうる。

## Context

現 adapter は `submit → register → deploy → predict` の4操作
（`src/platforms/shared/contracts/ports.py`）で、各基盤のパイプラインのステップとほぼ1対1。
技術的な載せ替え自体は可能というのが親調査 §5.1 の見立て。**問題は実行の所有者が移ること**で、
`ml_runs` の行は adapter が能動的に `_tracked()` を呼んで生まれる（`contracts/tracking.py`）。
パイプラインが実行を所有すると呼び出し点がステップ内部へ移り、attempt / failure_class を
今の粒度で取れるかが未知。結合点は C-1 `_tracked()` / C-2 `job_owns_success` / C-3 `job_record.py` の3つ。

着手前に押さえた現状（2026-08-02 実測）:

| 事実 | 値 | 意味 |
|---|---|---|
| `kfp` が依存に無い | `pyproject.toml` の `gcp` extra は `google-cloud-aiplatform` と `google-cloud-artifact-registry` のみ | **パイプライン定義には kfp の追加が要る**。依存追加は本体 extra ではなくブランチ内で完結させる |
| 学習イメージは Tier A 3基盤共通 | `make docker-build` | 同じイメージをカスタムコンポーネントに載せられる（H-2 の前提） |
| `job_record` は argparse の CLI | `src/platforms/neon/job_record.py:181` `build_parser()` / `:202` `main()` | シムとして同じ引数で呼べるかを H-2 で見る |
| 5基盤の baseline run は `code_revision` を解決できない | `PRE_HISTORY_RESET_REVISIONS`（2026-08-02 の履歴リセット） | **実験 run は新履歴の SHA を持つので機械的に区別できる**。分離の識別子として使える |

## Scope

- ブランチ `experiment/vertex-pipelines`（名称は着手時に確定）
- Vertex AI Pipelines のパイプライン定義1本。**train → register の2ステップで十分**
  （deploy / predict は H-1 / H-2 の判定に不要なら省く。常時課金を避ける）
- `kfp` 依存の追加（ブランチ内のみ）
- 判定結果を本ノートに記録し、続行 / 撤退を owner に諮って decision-log に残す

## Non-scope

- SageMaker / Azure ML への横展開（Vertex の結果を見てから）
- main への統合・既存 adapter の変更
- マネージド実験管理（Vertex Experiments 等）——パイプラインの結果次第で別タスク
- `sql/comparison_queries.sql` の変更（実験行が本番クエリに混ざらない設計にするのが先）

## Plan

1. **owner 承認を取る**（Heavy・課金あり・§Owner-only Decisions の2点を先に決める）
2. ブランチを切る。`kfp` を追加し、**compile だけ**（`--dry-run` 相当）で1本通す。ここまで課金ゼロ
3. **H-2 を先に見る**: 既存学習イメージのカスタムコンポーネントから
   `python -m platforms.neon.job_record` を同じ引数で呼ぶ。通れば C-3 の結合は薄い
4. **H-1 を見る**: パイプラインを1回実行し、`ml_runs`（または Neon branch）を SELECT して
   6列のどれが埋まりどれが空かを表にする
5. **失敗も1回は観測する**（学習を意図的に落とす）。`attempt` と `failure_class` は
   成功だけ見ても埋まるか分からない —— ここが H-1 の核心
6. リソースを destroy し、`scripts/check_residual.py` で残留ゼロを確認
7. 判定表を本ノートに追記 → owner に続行 / 撤退を諮る → decision-log に記録

## Acceptance Criteria

- [ ] `ml_runs` 6列の充足が**列ごとに埋まった / 埋まらなかった**の表として本ノートに載る
      （「だいたい取れた」で終えない）
- [ ] **失敗ケースを1回以上観測**し、`attempt` / `failure_class` の可否を明記
- [ ] H-2 の可否（`job_record` シムがそのまま呼べたか）と、呼べなかった場合の理由
- [ ] 実験行が本番 `ml_runs` の比較クエリを汚していないこと（§Risk の分離策が効いた実測）
- [ ] `check_residual.py` で残留ゼロ（課金が続くものが無い）
- [ ] 続行 / 撤退の owner 判断が decision-log に記録されている
- [ ] main が無変更（`git diff main` が空）

## Stop / Ask Owner If

- 判定に **deploy / predict まで必要**と分かったとき（常時課金が発生する）
- 実験行が本番 `ml_runs` に分離なしで入ったとき（→ Rollback Trigger）
- 想定コストを超えそうなとき（§Risk）
- 「6列は埋まらないが載せ替えたい」という結論になったとき
  —— **比較ラボとしての退行を受け入れるかは owner 判断**で、実装側で決めない

## Risk

- **記録の意味論が壊れる**: パイプライン実行の行が既存 `ml_runs` に混ざると比較クエリ5本が濁る
  （修正02 の教訓そのもの）。→ 対策: Neon branch を切るか、`code_revision` で分離する。
  後者は履歴リセットにより **baseline 5件が `PRE_HISTORY_RESET_REVISIONS` として名指しされている**ので、
  新履歴の SHA を持つ実験行と機械的に区別できる
- **コスト**: Pipelines の実行課金 + 一時リソース。1回の試行は数百円レンジの想定。
  deploy まで進めると常時課金に変わる（→ Stop 条件）
- **判定が「どちらとも言えない」で終わる**: 失敗ケースを観測しないと attempt / failure_class の
  可否が分からない。Plan 5 を省かない

続行 or 撤退の owner 判断が decision-log に残り、リソースが destroy 済み。

## Rollback Trigger

- 実験行が本番 `ml_runs` に分離なしで混入したら、即座に該当 `code_revision` を特定して報告
  （削除するかは owner 判断。「計測データを消さない」規約との調整）
- 常時課金リソースが意図せず立ったら即 teardown し、`check_residual.py` で確認

## Evidence Required

**Level 4**（実クラウドの観測）: パイプライン実行の実ログと、`ml_runs`（または branch DB）の
SELECT 結果。成功 run と失敗 run の両方。判定表は本ノートへ。
