## Goal

`ml_runs`（Neon）が担う記録のうち、どこまでを Vertex AI Experiments で代替・併用できるかを
**まず調査で**確定し、A / B / C のどれかを owner に提案する。

- **A. 併存**: Experiments には基盤内の詳細、Neon には比較6列。二重記録のコストを払う
- **B. 置換**: Neon をやめ、横断集計層を新設する
- **C. 不採用**: 使わない。理由を記録して閉じる

## Value

docs canonicalization / failure detection。「自前 `ml_runs` を維持するか」を推測でなく
根拠付きで決める。あわせて Experiments というマネージド機能を1回は触って学ぶ（学習ラボの目的）。

## Context — 再調査で静的に確定したこと（2026-08-02・コード実読）

### 共存は設計上すでに保証されている

記録先は `RunSink` **Protocol**（`core/telemetry/tracking.py:85`）で抽象化済み。
`NeonRunSink` / `JsonlRunSink` が既にこの契約の下で差し替わっている（write_path の
direct / collected はこの差し替えそのもの）。**Experiments を「追加の sink」として
足す形なら、Port 契約・Tier B adapter・`ml_runs` スキーマに一切触れない。**
つまり A（併存）の実装可能性は実験不要で Yes。

### B（置換）は静的に敗着と分かる

1. **UC-003「Neon の SELECT だけで5基盤比較」が単一テーブル前提。** Experiments は
   1基盤の中で実験を並べるサービスで、SageMaker / Azure ML には別物の実験管理がある。
   置換すると横断集計層（＝新たな自前実装）が必要になり、「自前を減らす」目的と矛盾する
2. **attempt の意味論が壊れる。** attempt は `sink.next_attempt()` = **Neon の同一
   (platform, stage) 過去行数 + 1**（`tracking.py`）。置換するとこのカウントの正本ごと
   再実装になる。permission friction（本ラボ本命）の土台がここ
3. 6列のうち `platform / attempt / failure_class / write_path` は Experiments に
   **一級のスロットが無い**（generic な params / labels に押し込むだけ）。
   「格納できるか」の答えは Yes だが「比較の軸として引けるか」の答えは No

→ **判定は実質 A か C の二択**で、どちらも調査で決められる。

### 唯一実測でしか分からないこと

Experiments の実際の使い勝手（UI での見え方・SDK の記録コスト・ML Metadata 課金の実感）。
これは A の「二重記録コストを払う価値があるか」の材料になるが、**任意**。
C で閉じるなら実測ゼロで完了できる。

## Scope

- 任意: A に傾いた場合のみ、成功 run 1本を Experiments へ記録するスモーク（要 owner 承認・数百円）

## Stop / Ask Owner If

- 調査の結果 **B が敗着でない**と分かったとき（§Context の3論点のどれかが崩れたとき）
- スモークに進みたくなったとき（クラウド課金の発生＝owner 承認）
- Experiments 対応のために `RunSink` 契約や `_tracked()` を変えたくなったとき
  （追加 sink で足りないなら、それ自体が C の根拠）
