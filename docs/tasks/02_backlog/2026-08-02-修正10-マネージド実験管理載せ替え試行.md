## Goal

`ml_runs`（Neon）が担っている記録のうち、**どこまでを Vertex AI Experiments で代替できるか**を
実測で確定する。判定の単位は「本ラボが比較に使っている6列」。

| 列 | 何に使っているか | Experiments で持てるか（← これを測る） |
|---|---|---|
| `platform` | 5基盤の横断比較の軸 | ？ |
| `stage` | stage 別所要の集計 | ？ |
| `status` | 成功/失敗の判定 | ？ |
| `attempt` | **permission friction（本ラボ本命）** | ？ |
| `failure_class` | 詰まりの原因分類（sdk 12 / container 1 …） | ？ |
| `write_path` | direct / collected の到達経路 | ？ |

**答えが「全部持てる」でも載せ替えが正解とは限らない**（§Risk）。判定と意思決定を分ける。

## Value

docs canonicalization / failure detection。「自前の `ml_runs` を持ち続けるか、マネージドに寄せるか」を
実測で決める。放置すると「マネージドで足りるのに自前を維持している」か、その逆かが分からないまま
運用コストだけ払い続ける。

## Context

### 現状（2026-08-02 実測）

| 事実 | 根拠 |
|---|---|
| **Vertex AI Experiments は未使用** | `src/platforms/vertex/adapter.py:4` の docstring に「SDK に残る: Custom Job / Experiment / Model Upload / Deploy」とあるが、実装で Experiment を呼んでいる箇所は無い |
| **Model Registry は既に使用中** | `adapter.py:207` `self.sdk.Model.upload(...)`（register stage）。＝マネージドの記録面を**部分的には既に使っている** |
| 記録の正本は Neon | `ml_runs` / `infra_events`。5基盤を1つのテーブルで比較できることが要件 UC-003 の前提 |
| 記録は adapter が能動的に書く | `src/platforms/shared/contracts/tracking.py` の `_tracked()`。成功行だけジョブ側が書く（`job_owns_success`） |

### この問いの本質

Experiments は **1基盤の中で実験を並べる**ための仕組みで、本ラボが必要としているのは
**5基盤を1つの軸で並べる**こと。基盤ごとの実験管理に寄せると、
`sql/comparison_queries.sql` の5本が拠って立つ「単一テーブル」が消える。

したがって現実的な着地は次の3つのどれかで、**どれになるかを決めるのがこのタスク**:

- **A. 併存**: Experiments には基盤内の詳細（params/metrics/artifact）、Neon には比較6列。二重記録のコストを払う
- **B. 置換**: Neon をやめ、5基盤の Experiments を横断集計する層を作る。集計層が新たな自前実装になる
- **C. 不採用**: Experiments は使わない。理由を記録して閉じる

- Model Registry の扱いの変更（既に使用中。本タスクは追跡面だけを見る）

- 過去 run の Experiments への移送（「計測データを消さない」規約と別問題。やらない）

## Plan

1. **owner 承認を取る**（Heavy・課金あり）
2. ブランチを切る。Experiments への記録は `google-cloud-aiplatform`（既存依存）で足りるはずなので、
   **依存追加が要るかをまず確認**する
3. **成功 run を1本記録**し、6列それぞれをどう表現したか（できなかったか）を書き出す
4. **失敗 run を1本記録**する。`attempt` と `failure_class` は成功だけ見ても可否が分からない
   —— ここを省くと本ラボ本命の permission friction の判定が空振りする
5. 5基盤横断で並べられるかを確認する（1基盤だけ見て「使える」と結論しない）
6. A / B / C を判定し、根拠とともに本ノートへ記録 → owner 判断を decision-log へ
7. リソースを片付け、`scripts/check_residual.py` で残留ゼロを確認

## Acceptance Criteria

- [ ] 6列それぞれについて **表現できた / できなかった / 代替表現がある** が表で埋まっている
- [ ] **失敗 run を1回以上記録**し、`attempt` / `failure_class` の可否を明記
- [ ] 5基盤横断で並べられるかの判定（1基盤の結果だけで一般化していない）
- [ ] A / B / C のどれかに決まり、**選ばなかった2つを退けた理由**が書かれている
- [ ] `check_residual.py` で残留ゼロ
- [ ] owner 判断が decision-log に記録されている
- [ ] main が無変更（`git diff main` が空）

## Stop / Ask Owner If

- 判定に **B（置換）の実装**が必要と分かったとき —— 横断集計層は新規アーキで別タスク
- Experiments への記録のために **adapter の `_tracked()` を変える**必要が出たとき
  （記録の意味論に触れる。修正02 の教訓）
- 過去データの移送が選択肢に上がったとき（「計測データを消さない」規約との調整が要る）
- 想定コストを超えそうなとき

## Risk

- **二重記録で正本が2つになる**（A を選んだ場合）。どちらが正かが曖昧になると、
  レポートの数字の出所が追えなくなる。→ 対策: 選んだ時点で「比較の正本は Neon」を
  `docs/specs/` に明記してから実装する
- **1基盤の結果で一般化する**: Vertex で足りても SageMaker / Azure ML の実験管理が
  同じ表現力を持つとは限らない。→ 対策: Acceptance に横断判定を入れてある
- **コスト**: Experiments 自体は ML Metadata の課金で小さいが、記録のために学習ジョブを
  回す分がかかる。想定は数百円レンジ
