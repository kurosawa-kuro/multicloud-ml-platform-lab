## 再調査の結論（先に答え）

**Tier B（Snowflake / Databricks）・Core との共存は、実験せずとも設計上保証されている。**
初版が「未知」とした H-1 / H-2 は、コードを読めば大半が確定した。
オーケストレータは最初から Core の外にあり、この改修に耐える設計に**既になっている**。

| 初版の仮説 | 再調査の答え | 根拠 |
|---|---|---|
| H-1: `ml_runs` 6列がマネージド実行でも埋まるか | **埋まる（構成上）** | 6列を書くのは adapter（`_tracked()`）と学習コンテナ内の `job_record` で、**どちらもパイプラインが触らないコードのまま動く**。attempt は `next_attempt()` = Neon の過去行数+1 の**プロセス外カウント**なので、誰がオーケストレートしても意味論が変わらない（`tracking.py:87`）。KFP の step retry も「再実行 = コードが再度数える = 新 attempt」で正しい |
| H-2: 既存イメージ + `job_record` シムをステップから呼べるか | **呼べる（静的に確定）** | `job_record` は**学習コンテナ内の entrypoint シム**が呼ぶ（`docker/training/entrypoint_vertex.sh`）。パイプラインは学習ジョブの中身に触れない。またパイプライン側ステップも、KFP の container component は任意イメージ・任意コマンドを実行できる（機能仕様） |
| C-1/C-2/C-3 の結合で載せ替えに Core 変更が要るか | **要らない** | 下記 |

### なぜ Core 変更ゼロで載るか

1. **オーケストレータは既に Core の外。** `PlatformAdapter`（`ports.py`）は5操作の形だけを
   規定し、呼び出し元を規定しない。現在の呼び出し元 `scripts/run_phase.py` はただの script
2. **全 stage が別プロセスで独立実行できる**（修正07 の成果）。
   - register: `artifact_uri` を Neon から resume（`resume.latest_artifact_uri` + tree-hash 互換ガード）
   - deploy: `model_ref` を Neon から resume（`latest_model_reference`）
   - predict: endpoint を **display_name で引き直す**（`vertex/adapter.py:253`。in-process 状態不要）
   - つまり **パイプラインの各ステップ = 既存イメージで `run_phase.py vertex <stage>` を1つ実行**、
     という合成だけで組める。ステップ間の受け渡しは既に Neon 経由で設計済み
3. **Tier B は additive change の外側。** 追加されるのはパイプライン定義（新規ファイル）と
   ドライバだけで、Port / `tracking.py` / `job_record` / `ml_runs` スキーマは不変。
   Databricks / Snowflake adapter は誰が Vertex を回しているかを知らない

### env-conf での制御は要るか（owner の問いへの答え）

**必須ではない。** 「パイプライン的にふるまうか否か」は adapter の性質ではなく
**起動時にどのドライバを呼ぶかの選択**（`make phase-train` ↔ 将来の `make pipeline-run`）。
adapter は同じコードが動くので、実行時フラグで分岐させるものが無い。
`env/config.yaml` に `orchestrator: cli | pipeline` を足すのは「単一入口で切り替えたい」
場合の任意オプションであって、共存の条件ではない。**むしろ config 分岐で adapter 内部に
if を増やす方が、比較の透明性（1操作=1行の意味論）を濁らせる。**

### 守るべき不変条件（これに触れる変更案が出たら Stop）

- `PlatformAdapter` の5操作の形（`ports.py`）
- 行の所有規約: 学習成功行はジョブ側・投入失敗行は adapter 側（`job_record.py` docstring）
- attempt = Neon の過去行数 + 1（プロセス外カウント）
- `ml_runs` スキーマと `sql/comparison_queries.sql`
- `job_record` の CLI 引数契約（entrypoint シム3枚が既に依存）

## Goal（縮小後）

パイプライン定義1本（train → register で十分）を **compile まではローカルで**組み、
最後に1回だけ実行して次の3点を確認するスモーク。仮説検証の実験ではない。

1. ステップコンテナ → Neon の egress（CustomJob と同クラスの想定・高確度だが未実測の唯一の仮定）
2. パイプラインラッパのオーバーヘッド（所要・コスト）
3. ステップ失敗の見え方（UI / ログ）と、`ml_runs` の failure 行が二重にならないこと

## Value

docs canonicalization。「載せ替えても計測は保てる」が確定したので、問いは
**「保った上で、パイプライン化で何が得られるか」**（DAG 管理・キャッシュ・スケジュールの価値 vs
定義の維持コスト）に変わった。スモークはその判断材料の実感値を足す。

## Scope

- `kfp` の追加（**ブランチ内のみ**。`pyproject.toml` の `gcp` extra には足さない）
- パイプライン定義1本（各ステップ = 既存イメージ + `run_phase.py vertex <stage>`）
- compile（課金ゼロ）→ owner 承認 → 実行1回 → 観測3点の記録
- 判定を本ノートへ、続行/撤退を decision-log へ

## Non-scope

- 実験管理 → [修正10](./2026-08-02-修正10-マネージド実験管理載せ替え試行.md)
- SageMaker / Azure ML への横展開
- main への統合・adapter の変更（不変条件のとおり、**変更が要らないことが結論**）
- deploy / predict / teardown のパイプライン化（常時課金。観測3点に不要）

## Plan

1. ブランチを切り、`kfp` を追加。ステップを `run_phase.py vertex <stage>` の
   container component として定義し **compile を通す**（ここまで課金ゼロ・承認不要）
2. owner 承認を取り、1回実行（Spot・train → register のみ）
3. 観測3点＋ `ml_runs` の SELECT（成功行が1行ずつ・attempt が連番）を記録
4. `check_residual.py` で残留ゼロ確認
5. 判定と owner 判断を decision-log へ

## Acceptance Criteria

- [ ] compile がローカルで通る（パイプライン定義が既存イメージだけで組めたことの証明）
- [ ] 実行1回で `ml_runs` に train / register の行が**各1行**残り、attempt が Neon 基準の連番
- [ ] 観測3点（egress / オーバーヘッド / 失敗の見え方）が記録されている
- [ ] 不変条件に触れる変更が発生していない（`git diff main` に `src/` 変更なし。kfp 追加を除く）
- [ ] `check_residual.py` で残留ゼロ
- [ ] 続行 / 撤退の owner 判断が decision-log に記録

## Stop / Ask Owner If

- **不変条件のどれかに触れないと組めない**と分かったとき（＝再調査の結論が崩れたとき。
  その場合は本ノートの結論ごと書き直す）
- 実行前（承認ゲート）／想定コスト超過時
- ステップの二重記録など、`ml_runs` の意味論に濁りが観測されたとき

## Rollback Trigger

- 実験行が本番 `ml_runs` に分離なしで混入したら該当 `code_revision`（新履歴の SHA で
  機械的に区別可能）を特定して報告
